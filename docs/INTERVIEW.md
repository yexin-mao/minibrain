# Minibrain RAG 面试题与参考答案

这是一份可以直接用于复习和模拟面试的项目题库。答案不是通用概念摘抄，而是按
“**先给结论 → 再讲本项目怎么做 → 给实验或故障证据 → 主动说明边界**”组织。
面试时不必逐字背诵；先说每行答案的第一句，面试官追问时再展开数字和边界。

题目来自公开面经和 RAG 框架常见实践（来源见文末）。状态表示本项目对答案的支撑程度：

| 标记 | 含义 |
|---|---|
| ✅ **有数据** | 项目里有实测数字能撑，且能说出实验怎么做的 |
| 🟡 **有明确边界** | 原理和方案说得清，但缺少本项目的真实规模或人工数据 |
| ❌ **尚未覆盖** | 当前项目没有实现，也没有完成受控实验 |

完整系统数据流见 [`ARCHITECTURE.md`](ARCHITECTURE.md)，现场讲解顺序见
[`DEMO_GUIDE.md`](DEMO_GUIDE.md)。本文件聚焦“问题怎么回答”，开发候选项和历史取舍留在
[`BACKLOG.md`](BACKLOG.md)。

## 推荐答题结构

例如被问“为什么不用 cross-encoder 做默认重排”，不要只回答“延迟高”，可以说：

> Cross-encoder 能提高相关性，但是否默认启用要同时看排序质量、延迟和最终上下文成本。
> 我在固定 40 候选上做过消融，Complete Recall@5 从 0.707 提到 0.741，NDCG@5 从
> 0.886 提到 0.912；但检索 P50 从约 14ms 增到 1467ms，前五 context 还从 1062 字增到
> 2655 字。所以项目保留实验开关、默认关闭。这个结论只针对当前模型和语料，不代表
> cross-encoder 普遍不值得使用。

这段同时包含结论、实现、证据和边界，面试官容易继续追问，也不容易把自己逼进绝对结论。

## 一、切分（Chunking）

| 问题 | 状态 | 参考答案 |
|---|---|---|
| Chunk 怎么切？切大了切小了各有什么问题？ | ✅ | 网格实测（探针十三）：800 最优，1200 的 `CompRec@5` 掉 10~12 个点。**切大了的失败方式很具体**——同样 2400 字预算，1200 只装得下 15.3 个片段，800 能装 22.4 个，独立文档覆盖不全 |
| 为什么要 overlap？设多少？ | ✅ | **测出来设 0 最好，和通行建议相反**。overlap 对 Complete Recall 零影响，但 0 的 MRR 最高（0.966 vs 0.940）、片段还少 8%。原因：我们的切分按段落对齐，overlap 没活干，反而制造重复片段互相挤占 top-k |
| 不同文档类型分别怎么处理？ | ✅/🟡 | Markdown/DOCX/HTML 按标题层级；PPTX 按 slide；PDF 按 page，页码/幻灯片号进入 metadata 和引用位置；无标题文本退回段落/固定大小。🟡 在于 PDF 表格、OCR 和版面阅读顺序仍未做 |
| 语义边界切割 / 父子切割 / Late Chunking 了解吗？ | ✅ | 已实现 800 child / 1600 parent 并做三组受控消融。结论反直觉：有效的是 parent-aware child 去重（Recall@5 0.847→0.886，零 token 增长）；展开 parent 本身 Recall -0.004、token +469、答案支持零提升，所以默认只去重，完整展开是实验开关 |

> 固定粒度来自探针十三；父子切分没有把 child 拍成 400，而是保留实测最优的 800，
> 只把 parent 设成 1600。三组消融已经完成：flat child、child + parent 去重、small-to-big。
> 结果说明“父子检索”不能作为一个整体归因；候选去重有效，扩大正文无效。生产默认因此选择
> 第二组，而不是因为功能已经写了就强行开启第三组。
>
> ★ 这一节还留下一条**方法论**，比数字本身更值钱：
> **两把尺子量同一件事**。指标是按文件名算的，chunk 越小、同一文件切出的片段越多，
> 于是「top-5 个片段」覆盖的**不同文件**反而更少——那是粒度带来的结构性劣势，
> 不是检索更差。所以除了固定 k，还要固定**字符预算**再比一次
> （真正进 prompt 的是字符，不是片段数）。**两把尺子结论一致才下判断。**

## 二、向量检索与向量库

| 问题 | 状态 | 参考答案 |
|---|---|---|
| 向量检索原理是什么？ | ✅ | 余弦相似度；实测余弦计算只占本地开销 **0.1%**（0.10ms），真正的开销是数据搬运（101ms）——**这个反直觉的数字是自己测的** |
| 向量数据库怎么选？Milvus / FAISS / Qdrant / pgvector？ | ✅ | 选 pgvector，理由是**不引入第二个存储系统**；权限过滤能和向量检索写在同一条 SQL 的 WHERE 里，不用应用层后过滤（后过滤是最容易长越权 bug 的地方） |
| HNSW / IVFFlat 什么区别，怎么选？ | ✅ | 选 HNSW；IVFFlat 需要**先有数据才能建索引**（要算聚类中心），而 `schema.sql` 要求从空库幂等跑起，不兼容 |
| `ef_search` 怎么调？ | ✅ | **实测在 900 片段下调它完全无效**——ef 从 10 到 200，延迟和一致率一个样。能说出「为什么无效」比说出一个调参值更有说服力 |
| Embedding 模型怎么选？中文场景选什么？ | ✅/🟡 | 锁定 130 篇、719 chunks、58 题做 drop-in 对比：BGE-M3 相比 `qwen3-embedding-8b` MRL 1024，Recall@5 **0.796 vs 0.743**、NDCG@5 **0.791 vs 0.726**，本次语料编码约 **40s vs 128s**。因此 BGE-M3 是迁移候选；但尚未补公开集与端到端回归，不因单一自造集就直接切生产默认 |
| 换 embedding 模型要注意什么？ | ✅ | 维度必须和 `vector(1024)` 列、配置、检索逻辑一致；主索引 manifest 额外锁定 endpoint、model、dimension 和 MRL/L2 transform 版本，所以同维度换模型也会在检索/入库前 fail-fast，要求全量重建 |

### 这里有一个能讲很久的故事

**「你上了向量索引，它真的被用上了吗？」**

本项目在这上面翻过三次车，全部记录在 `eval/RESULTS.md` 探针十二：

1. 对照实验的两组**都走了全表扫描**，「精确 vs 近似」变成自己和自己比
2. 延迟测量没预热、按 ef 顺序测，测出「ef=20 比 ef=10 快」这种违反理论的结果
3. **HNSW 索引因反复 upload/purge 膨胀到 1125MB（表仅 18MB）**，优化器悄悄不用它、召回也跟着掉，**两件事都不报错**

第 3 个最值钱：我把这个**运维问题**当成「近似检索的召回代价」写进了文档，
而且它「正好符合理论预期」，所以差点没被发现——**能被发现纯粹是因为它复现不出来**。

> 这个故事能同时回答三个问题：「你怎么验证优化真的生效」「你踩过什么坑」
> 「你怎么保证数据可信」。**比任何一个漂亮的数字都有用。**

## 三、混合检索

| 问题 | 状态 | 参考答案 |
|---|---|---|
| 纯向量检索有什么问题？为什么要混合检索？ | ✅ | 实测：8 篇会议纪要的余弦相似度**全挤在 0.60~0.67，跨度仅 0.0738，MRR 只有 0.489**——向量对「前缀相同、只差编号」几乎无能为力，而 BM25 对 `MTG-20260617-02` 一击即中 |
| 反过来呢，什么时候 BM25 不行？ | ✅ | 产品型号 / 英文缩写 / 罕见人名三类，**向量是满分 1.000**，关键词反而被「同一个词出现在多篇」干扰。**强弱互补才是融合的理由，不是「都用上更保险」** |
| 两路结果怎么融合？权重怎么调？ | ✅ | 用 RRF（k=60），**不调权重**——两路的分数量纲不同（余弦 0~1 vs BM25 无上界），加权和没有可比性，RRF 只用排名 |
| BM25 的实现细节？ | ✅ | k1=1.5、b=0.75；主路径在 `mod_vector_li` 维护持久化全库倒排索引，sparse 与 vector 独立召回后 RRF。手写基线的同类索引实测比内存全量算**快 87.6 倍** |
| 中文怎么分词？为什么不用 jieba？ | ✅ | CJK 切二元组 + 拉丁词保留整体。**不用 jieba 的理由是测出来的**：二元组会产生「偶然稀有词」（「三年年假」切出「年年」），污染 BM25 的 IDF；所以只把**标识符类 token**（拉丁/数字）放进倒排索引 |
| 多路召回还有别的路吗？ | 🟡 | 只有向量 + BM25 两路。图检索、SQL 检索算另一条链路（table-rag） |
| 怎么确认混合检索每一步真的生效，而不是架构图上写了？ | ✅ | Web“检索实验室”直接跑生产检索并冻结每阶段快照：Dense 原始相似度、BM25 原始分数、RRF 融合分、去重移除数、可选 CE/MMR、parent 展开结果和各阶段耗时。早期快照立即复制，专门用测试防止 RRF 就地改分数污染观测结果；正常问答默认不构造轨迹 |

## 四、Rerank（重排）

| 问题 | 状态 | 参考答案 |
|---|---|---|
| Rerank 是什么？为什么检索之后还要重排？ | ✅ | 双塔 vs 交叉编码的区别；**触发条件是从指标里读出来的**：`Complete Recall@5` 只有 0.724 而 @10 是 0.948——信息在 top-10 里，没挤进 top-5 |
| 你为什么加 rerank？ | ✅ | **不是因为大家都加**。先算天花板：58 题里 12 题需要 ≥4 篇文档，k=3 时数学上拿不满，所以真实空间是 **k=5 的 0.207**，不是表面的 0.29 |
| 加了之后效果如何？ | ✅ | LLM listwise 的历史实验：等片数比 `CompRec@5` 0.793 vs 0.707（+8.6pp），但和真正送 10 片的 baseline 比是 0.793 vs 0.914（-12.1pp），延迟约 7.4 秒。因此运行时代码已移除，保留结果作为否决证据 |
| 那你直接把 k 调大不就行了？ | ✅ | **这正是对照组**：判据定成「rerank 20→5 要打赢 baseline@10，同时 context 字符数显著更少」。只赢指标不赢成本不算赢 |
| 用的什么 rerank 模型？效果如何？ | ✅ | 可选 `BAAI/bge-reranker-base` cross-encoder。企业集固定 40 候选后 Complete Recall@5 0.707→0.741、NDCG@5 0.886→0.912，但 P50 14ms→1467ms，前五 context 1062→2655 字；公开冻结 top-10 候选内 NanoNQ/NanoHotpotQA 也提升。结论是“排序有效但没省 context”，所以默认关闭、实验室可选，而不是因为做了就默认开 |
| 为什么不用 LLM 做 rerank？ | ✅ | 它既有位置偏见和结构化输出失败风险，又在最终回答前增加一次生成模型调用；本项目实测约 7.4 秒且没有打赢直接扩大 context 的 baseline，所以删除运行时实现 |

## 五、评测（这是本项目最强的一块）

| 问题 | 状态 | 参考答案 |
|---|---|---|
| 你怎么评估 RAG 的效果？ | ✅ | 58 题人工标注集 + 标准 IR 指标：Recall@k / Precision@k / HitRate@k / MRR / NDCG@k |
| Recall 和 Precision 在 RAG 里怎么算？ | ✅ | 手写实现（`scripts/ir_metrics.py`），20 个单元测试，**期望值是手算出来的**不是跑出来对齐的 |
| MRR 和 NDCG 有什么区别？ | ✅ | MRR 只看第一个相关文档的排名；NDCG 看全部相关文档的位置且带折损 |
| 标准指标够用吗？ | ✅ | **不够，所以自定义了两个**：<br>① `Complete Recall@k`——全部必需文档都进前 k 才算 1。因为「张敏的上级的上级」需要两篇文档，只召回一篇时 Recall 给 0.5 分，但用户拿到的是错答案<br>② `Top-k 一致率`——和精确检索的结果重合多少，用来量近似检索的代价，**跟标注质量无关** |
| RAGAS 这些框架用过吗？Faithfulness 怎么测？ | ✅/🟡 | 没有为了框架名硬接 RAGAS；结构化 LLM Judge 先过 4/4 校准。用 Qwen3-235B 独立重判 DeepSeek 的 8 个冻结答案：Correctness 0.850、Faithfulness 1.000、Citation 1.000、Relevance 0.975、拒答 1.000。随后用最新代码对 3 个失败/波动样本回归，五项均为 1.000；期间还发现并修复 Judge 把设计备注当证据、rubric 变化却复用缓存的问题。已生成盲标模板并支持 Cohen's κ/一致率/MAE；🟡 只剩真人标签未填写，因此仍不冒充人工真值 |
| 评测集怎么来的？会不会过拟合？ | ✅ | 手工标注。**没有独立验证集，所以明确规定不在评测集上调参**——好几个能提分的选项是主动放弃的，因为那是自欺欺人 |
| 你的评测出过错吗？ | ✅✅ | **七次「指标先于系统出错」**，全部留档。这是本项目最有说服力的一条：<br>标准答案标错笔数 / 覆盖率误判跨链路多跳 / 证据漏算 SQL / 扩语料后标注过期 / 对照组都走全表扫描 / 基准测试没预热 / 把索引膨胀当成算法特性 |

### 关于第七次，有一条方法论值得单独说

前六次的症状要么是「数字全都一样」，要么是「数字违反理论」——**都会让人起疑**。
第七次的症状是「数字正好符合理论预期」，反而**让人停止怀疑**。

> **测出反直觉的结果时要怀疑测量；测出「正好符合预期」的结果时，更要怀疑测量。**
>
> 由此立的硬规矩：**结论必须能复现两次才写进文档。**

## 六、幻觉与生成

| 问题 | 状态 | 参考答案 |
|---|---|---|
| RAG 的幻觉怎么处理？ | ✅ | 系统提示词要求每句话能指回证据；有 grounding 评测量「答案里有多少内容在证据里找不到」 |
| 检索不到怎么办？ | ✅ | 要求拒答并说明「已经查到了什么、还缺什么」，而不是硬编。**轮数用尽时也不返回「超过最大轮数」**，而是逼模型基于已有证据作答 |
| 你的拒答检测准吗？ | ✅ | **有已知假阴性**，比如「公司没有设立独立的运维部」这种表述匹配不上。**停止打补丁了，作为方法上限记录在案**——承认指标的边界比刷高它更诚实 |
| 怎么保证引用是真的？ | ✅/🟡 | 主路径确定性检查引用存在性、覆盖率以及数字/编号；离线独立 Judge 逐 claim 检查语义支持，8 题 Citation Correctness 为 1.000。前者可进 CI，后者有模型不确定性，虽已通过 4/4 校准，仍待人工盲标验证一致性 |

## 七、工程落地

| 问题 | 状态 | 参考答案 |
|---|---|---|
| RAG 端到端延迟怎么优化？ | ✅ | 分阶段实测：**embedding 网络往返占 92.4%**（1247ms），本地计算只占 8%。**所以换索引不会让用户觉得更快**——这个结论直接否掉了我原本排第一的优化项 |
| Token 成本怎么控制？ | ✅/🟡 | ✅ 检索先取 12 条候选，按相关性、独立文档覆盖和跨调用去重，在 cl100k_base 的 4000-token / 12-evidence 硬预算内组装；Run Trace 记录每条丢弃原因和供应商实际 usage。🟡 固定 tokenizer 不是 DeepSeek 的精确计费口径，尚未做金额报表 |
| 文档更新了，向量索引怎么更新？ | ✅ | 注册表保存规范化内容 hash 和版本号：同 source/文件名/内容直接返回原 ID，不重复 embedding；内容变化时原 ID `version + 1`、先删除旧 dense/sparse/parent 节点再异步重建。并发上传用 PostgreSQL advisory transaction lock 串行化 |
| RAG 缓存怎么防止越权和脏数据？ | ✅ | 只缓存短 TTL 检索结果；键包含 user_id、管理员身份、可见知识版本、query 和全部检索参数。不同权限不共享，文档 ready/更新/删除改变版本戳后自动 miss；返回深拷贝，evidence ID 不污染缓存 |
| 文档里的 Prompt Injection 怎么处理？ | ✅ | 工具结果统一包在 `<untrusted_evidence>`，系统规则声明它只是数据；高精度规则给疑似“忽略系统/泄露密钥”文本加警示但不静默删除。真正的数据隔离仍由 SQL 权限过滤保证，而不是指望 Prompt |
| 企业 Word 文档怎么接入？ | ✅ | 不按扩展名判断，先识别 OOXML ZIP 内的 `word/document.xml`；按 Word 块级 XML 顺序转 Markdown，保留 Heading 1–6、列表和表格，再复用结构感知切分。另有限制 20 MiB 上传、5000 个 ZIP entry、100 MiB 解压体积，空/图片型 Word 明确失败 |
| 企业 Excel 怎么接入？ | ✅ | XLSX 按 OOXML 包内容识别并自动路由 table-rag，不做向量化；原工作簿 `bytea` 只存一次，每个可见 Sheet 是独立 dataset/物理表，共享生命周期。支持重复表头消歧、numeric/boolean/date/timestamp/text 推断和前导零编号保护；未计算公式拒绝而不是静默导入空值，并有限制 Sheet/行/列/单元格/解压体积的护栏 |
| 权限怎么做？ | ✅ | 可见性判定**永远写在 SQL 的 WHERE 里**，不做查完再筛；连接池把 `search_path` 锁死在各自 schema，模块之间物理上够不着对方的表 |
| 设计一个面向 10 万用户的 RAG 系统？ | 🟡 | 已做本机 Compose 小压测：130 篇、20 并发 × 3 轮，60/60 成功，约 **5.19 QPS**；并发 P50 **829ms**、P95 **10.13s**。这只能暴露外部 Embedding 的高尾延迟，不能外推到 10 万用户；扩容方案见 `SCALING.md` |
| CI / 测试怎么做？ | ✅ | CI 起真的 PostgreSQL（不 mock 数据库——要验证的恰恰是 SQL 里的权限过滤）；发现过**三个测试在 CI 里空转通过**（没 key → 空文档目录 → `assert X not in 空集合` 恒真），其中一个是**权限测试** |
| 怎么把用户反馈变成持续改进？ | ✅ | 成功回答支持赞/踩、原因和备注；反馈按 `run_id` 关联完整证据与 Trace，同一用户重复提交 upsert。差评可导出为明确标记“需人工审核”的回归候选，补期望答案后才进入正式评测集 |
| 上线后监控什么？ | ✅ | 按权限聚合成功/失败、无证据率、p50/p95、token、平均证据、引用覆盖、差评和失败码；不展示尚未上报的缓存命中率，避免用假指标填仪表盘 |
| 如何交付和复现环境？ | ✅ | Docker Compose 编排 pgvector PostgreSQL、幂等 init、Web 和 Worker；db 健康且 schema 初始化成功后才启动业务服务，数据落具名卷 |

| 问题 | 状态 | 参考答案 |

## 九、选型、排障与生产追问

这一节补的是公开面试题里常见、但原题库没有单独列出的追问。答题时固定分三层：
先给 30 秒结论，再给本项目证据，最后主动说边界。**主动说边界不是示弱，
而是防止面试官把一个局部实验追问成无法自证的普遍结论。**

### 1. 为什么用 RAG，而不是微调或者直接塞长上下文？　🟡

- **30 秒回答：** RAG 适合频繁变化、私有、需要权限过滤和引用的事实知识；微调更适合改变模型行为、格式和领域表达，不适合充当可精确删除和更新的事实库；长上下文适合规模小、变化少且每次都能完整装入的材料。三者不是互斥关系。
- **项目证据：** Minibrain 的文档按 hash/version 增量更新，权限在 SQL 检索阶段过滤，答案能回指证据；这些都要求知识留在模型参数之外。
- **边界：** 没做 RAG vs 微调 vs 全量长上下文的同题成本实验，所以这是需求匹配结论，不冒充性能对照结论。

### 2. 用户说答案错了，怎么判断是哪一层的问题？　✅

- **30 秒回答：** 按“源文档 → 解析/切分 → 召回 → 融合/选择 → 生成/引用”逐层排查。先确认知识里有没有，再看目标文档是否进候选，最后看已有正确证据时模型是否仍答错；检索失败和生成失败的修法完全不同。
- **项目证据：** 文档状态保存 `parsed_as/error/chunk_count`；检索实验室冻结 Dense、BM25、RRF、去重、CE/MMR 各阶段；Run Trace 保存工具、入模证据、丢弃原因、claims、引用指标、延迟和 token。
- **边界：** 当前能定位到阶段，但还没有把“某次差评自动分类为解析/检索/生成故障”；差评导出后仍需人工审核。

### 3. Top-K 和相似度阈值怎么选？Dense 分数能跨查询比较吗？　✅

- **30 秒回答：** `candidate_k` 和最终入模 `k` 应分开；前者保召回，后者受 token、独立文档覆盖和延迟约束。Dense 分数受模型、语料和查询分布影响，不能把一个全局阈值拍脑袋用于所有模式，更不能直接和 BM25 分数比较，所以本项目用 RRF 融合排名。
- **项目证据：** 项目测过 @3/@5/@10 的 Recall、Complete Recall 和上下文成本；产品链路先召回 12 条候选，再按 4000-token / 12-evidence 硬预算组装。检索实验室同时冻结 Dense 顶分/分差、BM25 顶分、Dense-BM25 Top-5 重合度和 RRF 顶分，供后续校准。
- **项目证据：** 58 道可答题 + 8 道无答案题做固定 hash 的 75/25 切分。校准得到 Dense 0.339284，但 held-out 误拒 4/15（26.7%），无答案召回仍为 0%，所以分数硬门明确保持关闭；这是“相关性不等于可回答性”的实测证据。
- **边界：** 阈值只用于 observation；空结果和精确业务编号 metadata 未命中才确定性提前拒答，其余交给 claim 引用安全门。

### 4. 检索总会返回最近邻，系统怎么知道其实没有答案？　✅

- **30 秒回答：** “返回了最近邻”不等于“找到了答案”。生产上应组合相关性校准、目标事实覆盖、引用支持和拒答策略；不能只看最高余弦分数。
- **项目证据：** 检索层输出 `evidence_found / uncertain / no_evidence`。空结果与不存在的精确业务编号可确定性 no-evidence；分数阈值因 held-out 误拒 26.7% 而保持 report-only。生成后还有零额外 LLM 的确定性安全门：任一 claim 无有效引用、引用不存在、数字或业务编号不在对应证据里，就把答案替换为安全拒答。
- **边界：** “命中相关文档但该属性没写”无法由相似度判断，例如 Beta 项目文档相关度很高但没有预算；因此 uncertain 必须继续走回答与 claim 级校验。

### 5. 更换 Embedding 模型时怎么避免新旧向量混用？　✅

- **30 秒回答：** 必须把模型名、版本和维度视为索引 schema 的一部分。生产迁移应建新索引、全量回填、影子评测、切换读流量并保留回滚窗口，不能直接在旧列上边写边换。
- **项目证据：** `mod_vector_li.index_manifest` 锁定 endpoint、模型名、维度与 `mrl-head-l2-v1` 变换版本；首次空索引自动登记，旧非空索引必须由操作员显式 adopt，任何字段漂移都会阻止检索和新写入。`/health` 只暴露兼容状态，不泄露 endpoint。
- **边界：** 当前解决的是“禁止混写”，还没有双索引、影子流量和零停机切换；换模型仍需清空并全量重建。

### 6. 数据删除或权限变化后，如何保证索引和缓存同步失效？　✅

- **30 秒回答：** 权限必须在召回 SQL 内生效；删除要同时覆盖文档注册表、dense、sparse、parent 和缓存版本，不能依赖查询后过滤或等待 TTL 自然过期。
- **项目证据：** source/document 生命周期显式清理 LlamaIndex 节点、BM25 和 parent context；索引审计可检查孤儿；缓存键包含 user、管理员身份、可见知识版本和全部检索参数，更新、删除或 ready 状态变化后自然 miss。
- **边界：** 目前数据源来自手工上传，没有 Notion/Drive/Confluence 的外部删除事件或 CDC，因此能保证平台内生命周期，不能声称已解决外部源同步。

### 7. 同一用户并发提交同一个会话怎么办？　✅

- **30 秒回答：** Checkpointer 解决持久化，不自动等于解决并发。生产上应按 `thread_id` 串行化，配请求幂等键；可以选择数据库 advisory lock、分布式锁或每会话队列，重复请求返回已有结果，锁冲突则排队或明确 409。
- **项目证据：** 会话 id 服务端生成并校验用户前缀与 UUIDv4；问答期间持有 PostgreSQL session advisory lock，同 thread 冲突返回 `session_busy`（HTTP API 语义为 409，HTMX 适配层用可展示的错误片段响应）。浏览器为每次提交生成 UUID request ID，运行表用 `(user, session, request_id)` 唯一索引；成功响应丢失后重试会从 Run Trace 恢复结果，不再调用模型。
- **边界：** 当前选择“冲突返回 409”而不是排队；进程被强杀后，worker 启动恢复会把超时
  `running` 归档为 `stale_run_archived`。已成功请求可由 request ID 恢复，但运行中失败的请求
  不自动重放，避免不确定地重复模型调用。

### 8. 怎么防恶意文档、敏感信息和跨租户泄露？　✅/🟡

- **30 秒回答：** 三类风险分开处理：恶意指令靠“证据是不可信数据”的提示边界和红队测试；跨租户泄露靠检索 SQL 权限及缓存隔离；敏感信息还需要入库分类、脱敏、审计和输出策略，不能只靠 prompt。
- **项目证据：** 证据统一包进 `<untrusted_evidence>`，疑似注入文本会标警告但不当指令执行；普通用户/管理员可见性写进 SQL；模块连接池锁 `search_path`；缓存不跨用户共享，并有真实 PostgreSQL 权限测试。
- **边界：** 当前没有通用 PII/密钥识别和静态加密方案，所以跨租户与 prompt injection 有实现，企业级数据防泄漏只能讲设计。

### 9. RAG 延迟突然升高，先查什么？　✅

- **30 秒回答：** 先按阶段看 p50/p95，而不是先换向量库：入库队列、query embedding、dense/BM25、rerank、LLM 首包/总耗时、数据库计划和上游重试分别定位；同时区分冷启动、缓存失效和持续退化。
- **项目证据：** 实测 query embedding 网络往返占端到端 92.4%（约 1247ms），本地计算只占 8%，所以当时“优化索引”不是主要矛盾；监控页聚合 p50/p95、失败码、token 和无证据率，检索实验室记录检索阶段耗时，Run Trace 记录整次问答耗时、工具、证据和上下文取舍。
- **边界：** 当前是单机/Compose 级监控；只有 20 并发 × 3 轮的小压测，没有持续压测、分布式 tracing 和告警规则，不能报生产 SLO 容量。

### 10. 什么场景不应该使用 RAG？　✅

- **30 秒回答：** 需要精确聚合和事务一致性的结构化计算应走 SQL/API；需要改变输出风格或固定行为更适合提示工程/微调；极小且稳定的材料可以直接放上下文；需要执行真实世界动作时应调用受控工具，而不是让检索文本替代业务系统。
- **项目证据：** 项目专门保留 table-rag：销售合计、分组、筛选走只读 SQL，因为把表格切块再向量召回无法保证合计正确；GraphRAG、HyDE、LLM rerank 也都是实验后未强行塞进默认链路。
- **边界：** “不用 RAG”不是完全不用模型，而是让正确的数据范式负责正确的问题；最终选择仍取决于一致性、更新频率、可解释性、延迟和成本要求。

### 11. 为什么你的流式输出不直接逐 token 返回？　✅

- **30 秒回答：** 原始 token 一旦展示就无法撤回，而本项目要在生成后校验 claim 引用、数字和业务编号。因此用 SSE 流 started/heartbeat/completed/failed，最终答案通过安全门后一次发布；这是安全与首字延迟的明确取舍。
- **项目证据：** `/ask/stream` 是 POST SSE，10 秒心跳防代理空闲断开，关闭代理缓冲；异常只返回稳定错误码，chat cookie 仍由服务端生成。页面用 `fetch + ReadableStream` 消费，因为浏览器 EventSource 不支持 POST。
- **边界：** 这是“流式请求状态 + 最终答案”，不是 token streaming。若产品必须逐 token，需要先缓冲到 claim 边界或设计可撤回 UI，不能绕过 grounding gate。

### 12. 多 worker 入库时怎样避免重复处理和任务永久卡死？　✅

- **30 秒回答：** 数据库实体本身就是任务状态；领取用 `FOR UPDATE SKIP LOCKED`，处理期间续租，worker 崩溃后 lease 到期可被重新领取。临时错误指数退避，耗尽后进 dead letter；永久解析错误直接 failed。
- **项目证据：** 文档和表格链路共享 claim/process/renew lease 契约；worker 心跳间隔为 lease 的三分之一，`attempt_count/available_at/error` 可审计，页面支持 failed/dead_letter 人工重试。
- **边界：** 仍是 PostgreSQL 轻量队列，没有独立消息队列的吞吐、优先级和跨区域能力；当前规模下换 Celery/Kafka 没有收益证据。

### 13. 如何防止一次检索改动悄悄把效果做差？　✅

- **30 秒回答：** 单元测试只能证明算法按定义执行，不能证明检索质量不降；需要冻结公开集基线，并对新候选报告设置质量与延迟预算，超预算阻断合并。
- **项目证据：** CI 门禁覆盖 NanoNQ/NanoHotpotQA 的 hybrid MRR、Recall@5、Complete Recall@5、NDCG@10 和排除 query embedding 后的 P50；质量绝对下降超过 0.03 或延迟增长超过 50% 即失败。
- **边界：** CI 不持有付费 embedding key，所以不在线重跑公开集；检索策略变更必须在本地生成并提交 candidate。门禁能防“提交的报告已回归”，不能防开发者不重跑报告，因此 PR 纪律仍是边界的一部分。

## 面试时必须主动说明的边界

- 只做了本机 20 并发 × 3 轮的小压测，没有真实高并发和 10 万用户规模证据；`SCALING.md` 是设计分析，不是容量证明。
- 支持带文字层 PDF 的 page-aware 解析，但没有 OCR、复杂表格和版面阅读顺序还原。
- 没有 Notion、Google Drive、Confluence 等外部连接器及其删除事件/CDC。
- 端到端 Judge 已使用独立模型重判，但真人盲标模板尚未填写，因此不能把 Judge 分数当人工真值。
- embedding manifest 能阻止新旧向量混写，但还没有双索引、影子流量和零停机迁移。
- GraphRAG 只是有限语料上的对照实验，未接入多租户产品链路。

这些不会让项目失去面试价值。相反，主动区分“已实现、已实验、只做过设计”，能证明你理解原型和生产系统之间的距离。
