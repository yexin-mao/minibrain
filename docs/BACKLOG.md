### 补充建议：内容 hash 去重（成本最低、价值最实在）

`documents` 加一列 `content_sha256` + 唯一约束。

**为什么值得做**：同一份文档被传两次，索引里就有两套内容完全相同的片段。
它们的余弦相似度也完全相同，于是**一起挤进 top-k**，
把 5 个席位吃掉 2 个 —— 直接伤 `Complete Recall@5`（当前 baseline 只有 0.707）。

这不是理论风险：`minibrain-purge` 的存在本身就说明反复上传是常态。

成本：一个列 + 一次 `hashlib.sha256`。

### 补充建议：HNSW 索引膨胀检查

探针十二测出：反复 upload/purge 让 HNSW 索引膨胀到 **1125MB（表仅 18MB）**，
优化器悄悄不用它、召回跟着掉，**两件事都不报错**。

现在这条只写在文档里。而本项目立过一条规矩：

> **教训要写成代码里的检查，不能只写注释**（同一个坑因此踩了三次）。

所以应该有一个 `scripts/check_index_health.py`：
比对 `pg_relation_size(索引) / pg_relation_size(表)`，超过阈值就报警并提示 `REINDEX`。
可以进 CI，也可以在 `minibrain-purge` 之后自动跑。

成本：低。**这条是把方法论兑现成代码，性价比最高的一条。**

### ★ 一个架构决策，不只是解析问题：PDF 里的表格归谁？

本项目的立意是「一张报表切碎再向量召回回来，算不出正确的合计」，
所以表格走 table-rag、文档走 vector-rag。**但那条分界线目前是按文件类型划的**
（`.csv`/`.xlsx` 走表格，`.md`/`.txt`/`.docx`/`.pdf` 走文档）。

一份 PDF 季报里同时有正文和三张表。它整篇走了 vector-rag，
于是**表格被切碎向量化了 —— 正是这个项目论证过不该做的事**。

三个选项，各有代价：

| 方案 | 代价 |
|---|---|
| 表格抽出来自动建表送 table-rag | 表结构推断在真实 PDF 上很不稳，且要处理跨页表 |
| 表格保持原样但标记为「不可切分」，整块进一个 chunk | 简单，但大表会撑爆 chunk_size |
| 表格转成 markdown 后当正文切 | 现状的隐式做法，**已被本项目自己的论证否定** |

**这个决策要先想清楚再动手做 PDF 版式解析** —— 否则解析出来的表格不知道往哪送。

### 优先级建议

1. **内容 hash 去重** + **HNSW 膨胀检查** —— 成本最低，都是把已有教训固化
2. ~~**docx / xlsx**~~ —— 两者已完成内容识别和对应链路接入
3. **增量更新** —— 工程含量最高，且和 HNSW 膨胀那条教训直接相关
4. PDF 版式解析 —— 先解决上面那个架构决策
5. OCR / HTML / 大文件 —— 长尾，想做再做

| 部件 | 状态 | 说明 |
|---|---|---|
| 固定大小 + overlap | ✅ | 800 / 0，**测出来的**（探针十三） |
| **结构感知切分**（按 markdown 标题层级） | ✅ | ATX 标题层级 + fenced code 保护，标题路径写入 metadata |
| **父子切分 / small-to-big** | ✅ | 800 child / 1600 parent；消融后默认只做 parent-aware child 去重，完整展开为开关 |
| 上下文增强切分（每片加前缀） | ✅ | 标题路径前缀，零 LLM 调用 |
| 按文档类型分策略 | ❌ | 是上面几项的组合结果，不是独立部件 |
| 语义切分（相邻句 embedding 断点） | ⛔ | **建议不做**，理由见下 |

### 结构感知切分 —— 建议做

语料本身就是 markdown，`_first_heading` 已经在解析标题了。
让切分在标题边界断开，并把「标题路径」写进 chunk metadata
（例如 `绩效手册 > 第三章 > 3.2 考核周期`）。

**收益是双份的**：切分边界更干净，同时白送一份结构化元数据 ——
后面第四节的「元数据过滤」直接就能用上它。

成本：低。LlamaIndex 有 `MarkdownNodeParser`。

### 父子切分 / small-to-big —— 建议做

**小片段检索，大片段进 prompt**。检索时用 400 字的小片（语义集中、命中准），
命中后把它所属的 1600 字父片段送进 prompt（上下文完整）。

**为什么和这个项目特别搭**：探针十三测出 1200 字符明显最差，根因是
「同样 2400 字预算，1200 只装得下 15.3 个片段，800 能装 22.4 个，独立文档覆盖不全」。
父子切分正是这个矛盾的标准解法 —— **检索粒度和生成粒度解耦，不用二选一**。

成本：中。LlamaIndex 有 `HierarchicalNodeParser` + `AutoMergingRetriever`，
更轻的选项是 `SentenceWindowNodeParser`。

### 上下文增强切分 —— 建议做廉价版

原始做法（Anthropic contextual retrieval）：让 LLM 为每个片段生成一段
「这片在整篇文档里是什么位置、讲什么」的前缀，拼在片段前面再向量化。

**成本是每片一次 LLM 调用 —— 900 片就是 900 次，和 GraphRAG 建图同一个量级。**

**廉价替代（建议先做这个）**：不调 LLM，直接把
`文件名 + 标题路径 + 文档首个标题` 当前缀拼上去。
结构感知切分做完之后，这些信息**已经在 metadata 里了，零额外成本**。

它解决的是同一个问题：孤立片段里「本季度营收增长 12%」不知道是哪个季度、哪家公司。
先用零成本版本，如果将来测出还有空间，再考虑上 LLM 版。

### ⛔ 语义切分 —— 建议不做

做法是对每个句子求 embedding，相邻句相似度低于阈值就断开。

**不做的三个理由**：

1. 探针十三已测出 **overlap=0 最优**，根因是「切分按段落对齐，overlap 没活干」——
   说明当前语料的**自然边界已经很清晰**，语义切分要解决的问题不存在
2. 它改变的是**边界位置**，不是**粒度**。而探针十三的结论差异（800 vs 1200 差 10~12 个点）
   全部来自粒度
3. 成本是每个句子一次 embedding

**触发条件**：如果语料变成长篇无小标题的文本（合同、论文、访谈记录），
这三条理由全部失效，那时再做。写在这里是为了**「不做」也有据可查**。

### 时间 / 新鲜度字段 —— 建议做，成本最低

语料里有 `long-report-q1-张敏.md` 到 `q4`、`meeting-mtg-20260617-02.md`，
**时间信息就在文件名里**。抽出来存进 metadata，就能支持
「最近一次的季度报告怎么说」这类问题，也能给排序加新鲜度权重。

成本：一个正则 + 一个 metadata 字段。**和第四节的元数据过滤是同一件事的两半。**

### 文档级摘要索引 —— 建议做

两级检索：先用文档级向量（标题 + 摘要）选出候选文档，再在文档内部选片段。

**为什么和这个项目搭**：核心痛点是 `Complete Recall`（必须召回**全部**必需文档）。
现在是片段级竞争，一篇文档如果有 5 个相关片段，它们会互相挤占 top-k 席位，
**把另一篇必需文档挤出去**。两级检索天然保证「每篇文档至少有代表」。

这也正是探针十三留下的方法论「两把尺子」发现的那个结构性问题。

### ★ 假设性问题多向量 —— 建议做，但排最后

做法：对每个片段生成 3~5 个「这片能回答什么问题」，把**问题**的向量入库。
检索时是 query 对 query 匹配，而不是 query 对 answer。

**它是探针十四（HyDE 否决）的天然续集，这一点值得单独讲**：

| | HyDE | 假设性问题 |
|---|---|---|
| 直觉 | 问题和答案用词不同，所以造一个假答案去匹配 | 同上，反过来：造假问题去匹配真问题 |
| 造假发生在 | **查询侧**，基于模型记忆 | **索引侧**，基于真实原文 |
| 风险 | 问题越冷门，编得越离谱，检索被带偏 | 基于原文生成，不会脱离语料 |
| 成本 | 每次查询一次 LLM（在线） | 每片一次 LLM（**离线，一次性**） |

**同一个直觉，两种实现，一个被数据否决了 —— 那另一个会不会成立？**
这是很干净的实验设计，也是把探针十四那次否决讲得更完整的方式。

**但成本是约 900 次 LLM 调用**，和 GraphRAG 建图同量级。所以排最后。

### 框架版 BM25 退化 —— 已修复

原实现先用向量捞候选池，再在池内做 BM25，不是真正的独立 sparse 召回。
现在 `mod_vector_li.node_lexical_stats / node_terms` 在入库时持久化 BM25 统计，
关键词路和向量路分别从全库召回，再用 RRF 融合。权限与业务 metadata
都在 sparse SQL 的 WHERE 中过滤。旧节点可用 `minibrain-reindex-lexical`
回填，不重新切分或调用 embedding。

### ★ 元数据过滤 —— 你的判断是对的，而且比「有必要」更强

这不是锦上添花，**它直接打在项目已知的最大盲区上**。

探针一之二测出：真正的盲区不是「编号」，而是**「前缀相同、只差几位数字的编号」**。
问 `MTG-20260617-02`，前三名全是别的会议纪要，正确答案排第 8，
**Recall@5 = 1.000 但 MRR 只有 0.489 —— 问题在排序不在召回**。

对这个问题现在有两套解法：

| 解法 | 性质 | 效果 |
|---|---|---|
| BM25 混合检索 | **统计**解法 | 已做，MRR 0.489 → 1.000 |
| 元数据过滤 | **精确**解法 | 已做；规则过滤零命中时退回仅权限过滤 |

统计解法的问题是它依赖 IDF —— 而这个项目已经吃过一次亏：
中文二元组的「偶然稀有」（`天年` 是「三年年假」切出的伪词）污染 IDF，
所以最后只把标识符类 token 放进倒排索引。**统计解法天生是概率性的。**

元数据过滤是确定的：从问题里抽出 `MTG-20260617-02`，直接 `WHERE filename LIKE ...`，
命中就是命中。**两套解法并存，正是「强弱互补才是融合的理由」那条结论的延伸。**

当前做法：

1. **规则抽取**：`MTG-\d{8}-\d{2}`、`PRJ-\d{4}-\d{4}`、`TICKET-\d{5}`、年份、季度和文档类型
2. **没有 LLM 兜底**：避免为了“选证据”额外调用一次生成模型
3. **安全默认值**：抽不出来就不过滤；业务过滤零命中时退回仅权限过滤

★ 这个三段式和 companybrain 的 `mode_router` 是同一个骨架
（规则 → LLM 兜底 → 安全默认值），**而且那个骨架的设计理由你已经能讲**：
确定性问法用规则更准且零延迟、LLM 隔离在一层里好排查、降级终点保证不劣于改造前。

**依赖**：需要 metadata 里有可过滤的字段 —— 也就是第二节的结构感知切分
和第三节的时间字段。所以那两条要排在它前面或同时做。

### 历史记录：LLM rerank 曾接回主路径，现已移除

> 以下保留当时的实现与实验过程，**不是当前架构说明**。重新用两把尺子比较后，

4. `core.search` 恢复透传 `rerank_pool`
5. 送进重排的是**原始问题**，不是 HyDE 改写后的假答案（见 `chain.py` 里的注释）

新增 `tests/test_rerank_wiring.py`（12 个用例，不连库不调模型），
按项目规矩把这次的教训写成检查。**牙齿验证过**——人为复现三种断裂，各自都被抓住：

里有 `handwritten/rerank`。它现在是**产品路径上**的出站调用，

### 已有数据的重新解读（重跑前先看这个）

现有 json（58 题 / 130 篇）：

| arm | CompRec@5 | MRR | context 字符 | 延迟 |
|---|---|---|---|---|
| baseline@5 | 0.707 | 0.940 | 514 | 11ms |
| baseline@10 | 0.741（@10 是 **0.914**） | 0.940 | 1060 | 11ms |
| **rerank 20→5** | **0.793** | 0.943 | 476 | **7383ms** |
| rerank 10→5 | 0.759 | 0.975 | 494 | 6496ms |

★★ **判据可能在比错的东西。** 脚本里写的是
「rerank 20→5 要在 CompRecall@5 上超过 baseline@10（0.741）」——
那是 baseline@10 的**前 5 片子集**。可 baseline@10 实际往 prompt 里送 10 片，
它的操作性数字是 CompRec@**10 = 0.914**。

换尺子看：

- **等片数比**（都送 5 片）：0.793 vs 0.707 → **+8.6pp，这是真收益**
- **等「实际进 prompt」比**：rerank 5 片 0.793 vs baseline 10 片 0.914 → **输 12pp**，
  只赢在 context 少 55%

结论倾向：**rerank 在当前语料上买到的是「更省 context」，不是「更准」**，
而 1060 字符在这个规模下根本不是瓶颈，代价却是延迟涨 671 倍。

这和探针十三「两把尺子量同一件事，两把尺子结论一致才下判断」是同一条方法论
—— **而这次是判据自己踩了坑。** 如果坐实，这是第八次「指标先于系统出错」。

★ 另一个副产品观察：baseline@5 的 CompRec@5（0.707）≠ baseline@10 的 CompRec@5（0.741）。
纯向量不该这样，但走的是 RRF 混合，**候选池大小会改变融合后的排序**。这本身可写一条。

### MMR / 多样性去重 —— 已完成，但评测后默认关闭

MMR（Maximal Marginal Relevance）：选下一个候选时，
不只看它和 query 的相关度，还要**减去它和已选内容的相似度**。

**为什么和这个项目特别搭**：核心指标是 `Complete Recall@k`
——「全部必需文档都进前 k 才算 1」。而 top-5 最典型的失败模式，
就是**同一篇文档的 5 个相邻片段全挤进来**，把另一篇必需文档挤出去。

MMR 正是治这个的。而且它**零 LLM 调用、零网络往返**，
和 7.4 秒的 LLM 重排是完全不同的成本曲线。

实现放在融合之后，因而能在向量 + BM25 的最终候选集上统一选取；优先使用库内已有
embedding 计算冗余，取不到时确定性退回词项 Jaccard，不增加 embedding 或 LLM 调用。

但 NanoNQ / NanoHotpotQA 公开评测都没有收益：Hotpot Complete Recall@5
从 hybrid 0.82 降到 0.72。因此保留显式开关做研究，产品默认关闭。

### cross-encoder 重排 —— 已完成消融，默认关闭

`rerank.py` 的 docstring 里已经写好了理由：

> 如果评测证明重排有收益，再考虑换成专用 cross-encoder（更快更便宜）；
> 如果证明没收益，就省下了引入一个模型依赖的成本。

现在有两组数字：LLM 重排约 7383ms；本地 `bge-reranker-base` 在企业集 40 候选上
P50 为 1467ms。CE 把 Complete Recall@5 从 0.707 提到 0.741，但前五 context
从 1062 增到 2655 字，未实现“更少证据达到同等效果”。因此保留显式开关，默认关闭。

实现层还修掉了“每查询/每候选数重复加载 1.1GB 权重”的问题；现在单进程只有一个
底层模型实例。代价仍是引入项目第一个本地模型依赖（此前全部走 API）。

### 规则重排 —— 建议做，成本极低

system prompt 里已经有「权威来源规则」（组织架构/制度以文档为准，统计数字以表格为准）。
**那是在生成层做的，可以下沉到检索层**：命中权威来源的片段直接加权。

同理，新鲜度：有了第三节的时间字段，「最近的季报」可以在排序时体现。

## 六、上下文组装（Context Assembly）

**这一段已接入生产路径。** 向量工具先扩大候选池，组装器再决定哪些证据真正进入模型。

现状：`agent/tools.py:57` 的 `_format_evidence()` 把召回的片段**全量拼接**，
没有预算、没有去重、没有顺序策略。

| 部件 | 状态 |
|---|---|
| 唯一引用编号 `E1.1 / E2.1` | ✅ |
| **token 预算** | ✅，cl100k_base 固定口径，默认 4000 |
| **相邻片段合并** | ❌ |
| **重复内容去重** | ✅，跨工具调用按规范化正文 hash |
| **片段排序策略**（lost-in-the-middle 缓解） | 🟡，首条相关性 + 不同文档覆盖；尚未做 U 型位置重排 |
| 上下文压缩（只留相关句） | ❌ |

Run Trace 会记录每条候选的 selected / duplicate / token_budget / evidence_limit，
以及 candidate count、selected count、context tokens 和预算利用率。组装过程零 LLM 调用。

口径边界：`cl100k_base` 让 CI 和本地得到完全相同的 token 数，但当前生成模型可能是
DeepSeek/Qwen，因此这不是供应商的精确计费 token。它是组装硬预算的固定工程口径。

### 关于 lost-in-the-middle：要留位置，但当前规模测不出来

现象：同样的内容放在上下文不同位置，模型用起来效果差很多，且呈 **U 型**
—— 开头和结尾记得住，中间容易被忽略。

Liu et al. 2023 的实验（20 篇文档，只有 1 篇含答案，挪动它的位置），
GPT-3.5-turbo 的准确率大致是：

| 答案位置 | 准确率 |
|---|---|
| 第 1 篇 | ~75% |
| 第 10 篇（正中） | ~53% |
| 第 20 篇（末尾） | ~63% |
| *对照：一篇都不给（闭卷）* | *~56%* |

最刺眼的是那条对照线：**答案埋在正中间时，比压根不给资料还差。**

★ **但当前规模仍很难验证 U 型位置策略**：论文是 20 篇文档、几千 token，
本项目现在最多选择 12 条、4000 个固定口径 token。组装器已经记录位置和取舍，
但尚无证据证明把高相关片段刻意放到首尾能提升当前语料，因此不默认做 U 型重排。

所以定位是：**组装器里预留排序策略这个接口，但不假装它现在有收益。**
和 `SCALING.md` 对路由方案的处理是同一类 —— 知道边界在哪，
知道什么时候会撞上，但不在测不出差别的规模上做优化。

### 为什么这一段是地基

**rerank 的收益（省 context）只有在系统里存在「预算」这个概念时才成立。**
此前没有预算，省下来的 context 没人消费；现在组装器真正消费 token 预算，
cross-encoder 的“同等预算下能否装进更好证据”终于成了可以严谨重测的问题。

**这两件事是咬合的，第 0 步和第 1 步应该连着做。**

### ★ 结构化输出 —— 已完成，它把引用校验变成了确定性的

现在模型在自由文本里标 `[1]`，要校验「这个 `[1]` 是不是真的对应第 1 条证据」，
只能做字符串匹配 —— **而这个项目已经吃过一次亏**：
「子串匹配只能抓『少答』，抓不到『多答』」（doc-08 就是漏网的那个）。

主路径现在让模型输出结构化结果（`{answer, claims: [{text, evidence_ids}]}`），
引用校验就从「模糊匹配」变成「查表」。

证据编号不再按每次工具调用从 `[1]` 重置，而是一次运行内唯一的
`E1.1 / E2.1`。后端计算 citation coverage、citation validity，并检查每个
claim 中的数字和业务编号是否真的出现在它引用的原文里。这个过程不调用第二次 LLM。

**仍然明确保留的边界**：claim 列表本身由生成模型拆分，规则校验能证明“引用编号存在”
和“硬事实在原文中出现”，不能证明整句与原文在语义上蕴含。后者仍需人工标注或
LLM-judge，不能把 citation validity 冒充 faithfulness。

**这一条的价值在于它把一个 🟡 变成确定性的 ✅，而不是引入一个新的不确定裁判。**
和这个项目「第一个数字必须绝对可复现」的偏好一致。

### 廉价 groundedness 检查 —— 已接入主路径

`RESULTS.md` 末尾已经写好方案：

> 把答案里出现的数字抽出来，检查是否都能在检索到的原文里找到。
> 抓不了全部幻觉，但**零成本、可复现、能进 CI**。

### Faithfulness（LLM-judge）—— 独立重判完成，待人工复核

动机已经论证完，不需要「因为大家都用 RAGAS」：

> 确定性字符串匹配能可靠地测「有没有出处」，测不好「有没有拒答」——
> 数字和编号是离散可穷举的，而「我不知道」在自然语言里有无穷多种说法。

拒绝它的四条代价也已经列好（不确定性叠加 / 分数没法调试 / 要联网花钱 / 进不了 CI）。

实现位于 `scripts/eval_answer_quality.py` 和 `minibrain.evaluation.answer_quality`。
它不只输出一个分数，而是重新从答案抽取全部事实，逐条返回支持状态、证据编号和理由；
另行检查生成模型提交的每个 claim 是否被它引用的正文语义支持。正式题开始前先跑
4 条人工标注样例，校准失败直接中止；Judge 响应按完整输入缓存，生成与裁判 token 分账。

现在已经有 `--require-independent-judge`、不暴露 Judge 结果的人工盲标模板，以及
分类一致率 / Cohen's κ / 连续分数 MAE 的计算脚本。Qwen3-235B 已对 DeepSeek 生成的
8 个答案完成独立重判：4/4 校准、8/8 成功，Correctness 0.850、Faithfulness 1.000、
Citation 1.000、Relevance 0.975、拒答 1.000。尚未完成的是由真人填写盲标模板，因此
这些结果只能称为独立模型评估，不能称为人工验证。
**这比任何 Faithfulness 分数都好讲** —— 因为这个项目的招牌就是「怀疑自己的指标」。

**为什么没有直接标成完成**：实现评测器和换一个模型当裁判都不等于人工真值。只有
真人盲标并核对一致率后，面试文档里的状态才能从 🟡 改成 ✅。

## 八、明确决定不做的

| 项 | 理由 | 触发条件 |
|---|---|---|
| 语义切分 | 探针十三已证明当前语料自然边界清晰（overlap=0 最优）；它改边界不改粒度，而结论差异全来自粒度 | 语料变成长篇无小标题文本 |
| LLM 版上下文增强切分 | 每片一次 LLM = 约 900 次调用；廉价版（文件名 + 标题路径）零成本拿大部分收益 | 廉价版测出仍有明显空间 |
| Neo4j / LightRAG | 换存储会引入额外变量，破坏与向量链路的受控对比 | 要做生产级 GraphRAG |
| 三级组织权限 | 权限**深度**不输（SQL WHERE 里判、连接池锁 search_path），差的是业务**层数** | 有真实多团队场景 |
| ~~Docker Compose 多服务~~ | 已补齐 db → init → Web/Worker 的健康检查启动顺序和持久化卷 | ✅ 已完成 |
