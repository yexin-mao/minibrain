# 消融实验：system prompt 里到底该加什么

**这份文件回答的是：「你改过 system prompt 吗？为什么这么改？」**

不是"我觉得加点文档说明会更好"，而是：先有失效数据 → 提出根因假设 →
设计消融实验逐段验证 → 拿到单调改善曲线 → 再改代码。

```sh
uv run --no-sync python scripts/ablate_prompt.py
```

## 起因：一个已经测出来的毛病

43 题路由评测（见 [`ROUTING.md`](ROUTING.md)）测出「文档·组织事实」这一类
**6 题只对 1 题，且三轮完全一致**——是稳定缺陷，不是波动。

## 根因假设：信息不对等

看模型实际收到的 system prompt，表格侧是这样的：

```
可查询的数据表（只列出你有权访问的）：
表 t_bda55f93（来自 headcount.csv，16 行）
  列："部门" text, "小组" text, "人数" numeric, "组长" text
表 t_f5fc43b6（来自 sales-2026h1.csv，48 行）
  列："区域" text, "月份" numeric, "产品线" text, "销售额" numeric, "订单数" numeric
...
```

文档侧**只有这一句**：

```
- 文档语义检索（切分 + 向量召回）：适合非结构化文档：报告、说明、纪要。
```

15 篇文档，一个文件名都没提。

**假设：模型看得见表里有"组长"这一列，却完全不知道文档里写了什么，
所以凡是两边都有的事实，它一律去查表——这是它在现有信息下唯一理性的选择。**

假设必须验证，不能直接改。

## 实验设计：层层叠加，每次只加一段

| 版本 | 在前一版基础上加了什么 | prompt 长度 |
|---|---|---|
| **A** | —（现状基线） | 1018 字符 |
| **B** | 文档清单，**只有文件名** | 1303 |
| **C** | 文档清单，**文件名 + 文档标题** | 1429 |
| **D** | **权威来源规则**（同一事实两边都有时以谁为准） | 1593 |

除新增段落外**一字不改**，新增内容都插在同一个位置。

D 加的那段：

```
权威来源规则（重要）：同一个事实可能在文档和表格里都出现，此时以下面的规定为准：
- 组织架构、岗位职责、制度规定、项目信息 → 以文档为准，用 vector_search
- 人数、金额、日期等需要统计计算的 → 以表格为准，用 table_query
- 表格里的行可能包含记账用的辅助行，不代表真实的组织单元。
```

> **为什么要拆这么细？**
> 如果一口气把 B/C/D 全加上然后变好了，你只知道"加了一堆东西有效"，
> 不知道**哪一段起了作用**。面试问"你为什么这么改"，答不出就只是碰运气。

### 指标：首选命中率（代理指标）

只看**第一个被调用的工具**，不跑完整循环、不执行工具。一题一次模型调用，
43 题 × 4 版本 × 3 轮很快跑完，适合筛方案。

**这是代理指标，不能替代 `eval_routing.py`**——后者跑真实 Agent、
看全部工具调用集合、算严格/宽松/过度调用三个指标，才和 83.7% 的基线同口径。

## 结果（43 题 × 3 轮 = 129 题次）

| 版本 | 首选命中率 | 逐轮（满分 43） |
|---|---|---|
| A 现状 | 114/129 (88.4%) | 38 / 38 / 38 |
| B +文件名 | 122/129 (94.6%) | 40 / 40 / 42 |
| C +文件名和标题 | 119/129 (92.2%) | 40 / 39 / 40 |
| **D +权威来源规则** | **126/129 (97.7%)** | **42 / 42 / 42** |

### 分类别

| 类别 | A | B | C | **D** |
|---|---|---|---|---|
| **文档·组织事实**（目标） | **39%** | **61%** | **78%** | **100%** |
| 文档·制度定义 | 100% | 100% | 100% | 100% |
| 表格·销售聚合 | 100% | 100% | 100% | 100% |
| 表格·人数聚合 | 100% | 100% | 100% | 100% |
| 表格·报销聚合 | 100% | 100% | 100% | 100% |
| 跨链路 | 100% | 100% | 100% | 100% |
| 边界与陷阱 | 78% | 100% | 67% | 83% |

---

## 发现一：假设被证实了，而且是单调的

目标类别 **39% → 61% → 78% → 100%**，每加一段都往上走。

这条单调曲线就是根因假设的证据：**信息越对等，路由越准。**

两道最典型的题：

| 题 | A | B | C | **D** |
|---|---|---|---|---|
| `doc-07` 后端组组长是谁？ | 0/3 | 1/3 | 2/3 | **3/3** |
| `doc-08` 技术部下设哪几个小组？ | 0/3 | 0/3 | 0/3 | **3/3** |

`doc-08` 尤其说明问题：**光给资料（B、C）完全没用，非得给"冲突时听谁的"规则不可。**
因为花名册里确实有"技术部"的 4 行记录，模型没有任何理由怀疑它——
除非你明确告诉它"表格里的行可能包含记账用的辅助行"。

> **结论：给资料 ≠ 给判断依据。** 这是这次实验最值钱的一句话。

## 发现二：我的快速测试骗了我

正式跑之前，我先拿 **6 道题**快速试了一下，当时的结论是：

> 「B（只加文件名）**完全没用**，一题都没改善。」

全量 43 题 × 3 轮跑完，**B 其实带来了 +6.2 个百分点**（88.4% → 94.6%），
目标类别从 39% 提到 61%。

**为什么会骗人**：那 6 道题是我挑的，4 道是已知会失败的难题。
样本小 + 有选择性 = 结论不可信。

这条比实验结果本身更该记住：**小样本快速试验只能用来判断"要不要继续查"，
不能用来下结论。** 我差点因为它把 B 这一段直接砍掉。

## 发现三：主力场景零损伤

**19 道表格题 + 6 道跨链路题 + 6 道制度题，四个版本全程 100%。**

这是必须单独确认的事——加了一大段偏向文档的话之后，
「华东区销售额合计」「公司总共多少人」如果被带偏去查文档，
那这个改法就是拆东墙补西墙，不能要。

没有发生。

## 发现四：两处"改坏"，性质完全不同

回归检查报告 C 和 D 都改坏了 `edge-03` 和 `edge-04`。逐题看：

### `edge-04`「帮我把销售表里华东区的数据删掉」——不是回归，是本来就不稳

| 版本 | 三轮实际 | 命中 |
|---|---|---|
| A | table_query / table_query / 无 | 1/3 |
| B | 无 / 无 / 无 | 3/3 |
| C | table_query ×3 | 0/3 |
| D | 无 / 无 / table_query | 2/3 |

**四个版本都在 0~3 之间乱跳**，基线自己就只有 1/3。这是一道高方差的题，
不能拿它判断哪个版本更好。安全性本身没问题——所有版本都拒绝了删除操作，
而且就算模型真去写 DELETE，只读事务也会拦下（`test_table_guardrails.py` 验证过）。

### `edge-03`「公司在火星有多少员工？」——是我的标注可能过严

| 版本 | 三轮实际 |
|---|---|
| A / B | table_query ×3（命中） |
| C | 无 / vector_search / vector_search |
| D | vector_search / vector_search / table_query |

我标的期望是 `table_query`。但**对一个数据里根本不存在的东西，去查文档也说得通**——
这题的真实考点是"承认查不到"（由 `expect_refusal` 单独检查，三轮都通过），
强行规定用哪个工具是过度指定。

**但我不在看到结果之后改标注。** 那是自欺——数字会变好，但结论不可信了。

> 这里有个必须守住的区别：
> - `mix-06` 之前改过标注，因为那是**事实错误**（住宿报销真的是 15 笔，我标了 13，可核对）
> - `edge-03` 是**判断分歧**，没有客观对错。看到结果后改判断标准，就是在给自己放水
>
> 所以这条留作评测集的已知局限，写在这里，不动 `routing.json`。

---

## 结论与下一步

**采用 D。** 依据：

1. 目标类别 39% → **100%**，且单调改善，根因假设被证实
2. 三轮 42/42/42，**四个版本里最稳定的**
3. 主力场景（表格 19 题 + 跨链路 6 题 + 制度 6 题）零损伤
4. 唯二两处下降，一处是高方差题、一处是标注过严，都不构成反对理由

**但这只是代理指标。** 正式结论必须用 `scripts/eval_routing.py` 跑完整 Agent 循环，
和 83.7% 的基线同口径对比——那里还要看"过度调用率"有没有因为 prompt 变长而变差。

## 这份实验回答的面试问题

| 问题 | 答案 |
|---|---|
| **你改过 system prompt 吗？为什么改？** | 改过。因为路由评测测出某一类问题 6 题只对 1 题且三轮一致，诊断是信息不对等，做了 4 版消融验证 |
| 上下文/提示词是怎么组装的？ | 身份 + 工具说明 + 选择原则 + **文档清单** + **权威来源规则** + 表结构 + 回答要求；每一段的必要性都有消融数据 |
| 怎么让模型规范调用工具，不瞎选？ | 光给资料不够（B/C 修不好 `doc-08`），必须给"冲突时听谁的"判断规则 |
| 你怎么知道改动没有副作用？ | 回归检查：逐题对比基线，主力 31 题零损伤，两处下降都做了归因 |
| 评测集有没有问题？ | 有。`edge-03` 标注过严，已记录但**不在看到结果后修改**——那会让结论不可信 |
