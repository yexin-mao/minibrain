# GraphRAG 假设书

> **这份文档写在动手之前。** 写完才开始搭，搭完再验。
>
> 之所以坚持这个顺序：如果动手之后再补理由，那理由不构成证据——
> 「多跳问题需要图遍历」这句话任何人不做都能说。
> 而事先写下「我预期它在哪类问题上赢、赢多少、代价是什么」，
> **哪怕结果是「没赢」，也是一个完整的实验**。
>
> 提交时间：这份文件的 git 首次提交时间早于 `modules/graph_rag/` 的任何代码。

## 为什么现在做（之前明确不做）

本项目一直的立场是「**没有数据支撑就不做**」，GraphRAG 因此被否决过，
理由记在 `eval/RESULTS.md` 探针二：

> 触发条件未满足——「Agentic RAG 之后仍解决不了的多跳」没有出现。

**这个理由有一个真实的漏洞。** 探针二证明的是「Agentic RAG **能解**多跳」，
它**不等于**「GraphRAG 不会更好」。这是两个不同的命题，而我从来没有
把两者放在同一批题上比过。

面试官只要追问一句「你怎么知道 GraphRAG 不会更好」，现在是答不上来的。

所以做这件事不是推翻原来的规矩，**是补上那条推理里缺的一环**。

---

## 假设一：它应该在「全局聚合」上明显赢

**预期赢，且这是最强的预期。**

`probe_agentic.py` 里有一组叫「全局聚合」的题（3 题），形如：

> 公司一共有几个部门？

向量检索在这类问题上有**结构性劣势**：答案不存在于任何单个片段里，
必须通读全库才能数出来。top-k 检索无论 k 多大都只是采样。

GraphRAG 理论上正好补这个：实体抽取阶段会把每个「部门」变成图上的节点，
数节点就是答案。

**判据**：这 3 题上，GraphRAG 的答对率要显著高于 Agentic RAG（当前 covered 率 0.22）。

## 假设二：它应该在「三跳以上」上赢一点

**预期小幅赢。**

`压力·三跳以上` 2 题 + `压力·链条到顶` 2 题。Agentic RAG 在这里的表现是
「能走通但浪费」——轨迹评测测出 `stop-03`（张敏的上级的上级的上级）
撞满 6 轮上限，第 4~6 轮的新增证据是 **0, 0, 0**。

图遍历天然不需要「查一次→读→再决定查什么」这个循环，**一次遍历到底**。

**判据**：同样答对的前提下，GraphRAG 的 LLM 调用次数要明显少于 Agentic RAG 的多轮。

## 假设三：它在「单点事实」上不会赢，甚至可能更差

**预期不赢——而且这条同样重要。**

`对照·单点事实` 3 题（「后端组有多少人？」）。答案就在一个片段里，
向量检索一次命中。GraphRAG 要先定位实体再遍历，**多绕一圈，还可能因为
实体抽取的误差丢掉原文细节**。

**这条是设计出来防止自我欺骗的。** 如果测出来 GraphRAG「在所有题上都更好」，
那大概率是实验设计有问题（比如两边用了不同的语料或不同的 embedding），
而不是它真的全面碾压。

## 假设四：数值计算类它一定不该用

`table-rag` 那条链路的题（「华东区销售额合计」）不在本次对比范围内。
图谱存的是关系不是数值，**拿它做聚合计算是用错工具**。

如果有人（包括模型自己）把这类问题路由到 GraphRAG，那是路由的 bug，
不是 GraphRAG 的锅。

---

## 成本必须一起量，这条最容易被跳过

GraphRAG 的建图成本是**数量级**的：每篇文档都要过一遍 LLM 抽实体和关系。

必须报出来的三个数：

| 指标 | 为什么必须报 |
|---|---|
| **建图的 LLM 调用次数 / token 数** | 130 篇语料要调多少次？向量入库是 0 次 LLM |
| **建图耗时** | 向量入库实测约 7 分钟（130 篇），图要多久 |
| **检索时的额外成本** | 图遍历要不要调 LLM？调几次 |

**如果它赢一点点但贵十倍，结论就是「不值得」——而这个结论同样值钱。**

RAG 面试里「什么时候该上 GraphRAG」的标准答案就是在讲这个权衡，
能拿出自己的成本数字，比背结论强。

## 技术选型：LlamaIndex `PropertyGraphIndex`，不是 LightRAG

对标项目 companybrain 用的是 `lightrag-hku 1.5.0` + Neo4j。这里刻意不跟：

**换存储会引入额外变量。** 本次要回答的是「图检索 vs 向量检索 vs Agentic」，
如果 GraphRAG 用 Neo4j + 它自己的 embedding，而向量链路用 pgvector + MRL 截断，
那测出来的差异里就混进了「存储不同、向量不同」——**和之前把
`MinibrainEmbedding` 包一层锁住 embedding 是同一个道理**。

用 `PropertyGraphIndex` 能做到：**同一份语料、同一个 embedding 函数、
同一套评测脚本**，只换索引结构。

面试被问到时的回答：「我知道 LightRAG，对标项目用的就是它。
我选 PropertyGraphIndex 是因为要做受控对比，换一套存储会引入额外变量。」

## 已知会做不干净的地方（先写下来，不假装没有）

**权限。** 图谱天然是跨文档的：实体和关系由多篇文档共同构成，
而这些文档可能属于不同的人、有不同的可见性。
「这条关系用户 A 能不能看」在图上没有向量库那么好回答——
向量库是一个片段对应一个 owner，图上一个节点可能来自五篇文档。

本次实验**不解决这个问题**，评测在单用户下跑。
但这是 GraphRAG 上生产的真实拦路虎，要在结论里写明，不能装作不存在。

## 判据总结

做完之后，下面三行必须都能填上具体数字：

1. 全局聚合 3 题：GraphRAG ___ vs Agentic RAG 0.22
2. 三跳以上 + 链条到顶 4 题：答对率 ___ ，LLM 调用次数 ___ vs Agentic 的 ___
3. 单点事实 3 题：GraphRAG ___ vs 向量检索 ___（预期不赢）

**三行里只要有一行填不上，这个实验就不算做完。**
