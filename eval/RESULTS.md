# 探针结果

这份文件回答一个问题：**这个项目的结论是测出来的，还是听来的？**

下面每个数字都由 `scripts/probe_*.py` 跑出来，原始输出在 `results/` 下。
重跑一遍就能复现——探针会自建用户、自灌语料、跑完自清理。

## 运行环境

| 项 | 值 |
|---|---|
| 日期 | 2026-08-03（15 篇语料） / 2026-08-05（扩到 84 篇） |
| embedding | `qwen/qwen3-embedding-8b`，MRL 截断到 **1024** 维 |
| 生成模型 | `deepseek/deepseek-v4-flash`（OpenRouter），temperature=0 |
| 切分 | 字符切分，chunk=800 / overlap=120 |
| 语料 | 初版 15 篇 / 1951 字符 → **现为 84 篇 / 18834 字节**（`scripts/gen_corpus.py` 生成，可复现） |
| 探针 | `probes.json` 10 题（人工设计）+ `probes_blindspot.json` 48 题（由植入的盲区词自动生成） |
| 检索 | 全量加载可见 chunk，内存 numpy 余弦 |

判定标准是**可计算的**，不需要人肉看效果，也不用 LLM 打分。

指标用 IR 领域的标准定义（`scripts/ir_metrics.py`，定义由 20 个单元测试钉死）：

| 指标 | 定义 |
|---|---|
| **Recall@k** | 前 k 个结果里命中了多少**比例**的相关文档 |
| **Precision@k** | 前 k 个结果里有多少比例是相关的（分母是 k） |
| **Hit Rate@k** | 前 k 个里**至少**命中 1 篇的查询占比 |
| **MRR** | 第一个相关文档排名的倒数，对所有查询取平均 |
| **NDCG@k** | 考虑排序位置的加权得分 |
| **Complete Recall@k** | ★ **非标准**的严格变体：前 k 个里命中**全部**相关文档的查询占比 |

最后一个是本项目自己定义的，明确标注为非标准。为什么需要它，下面用数据说明。

## 探针一：向量链路在什么问题上失效（15 篇语料，初版）

`uv run --no-sync python scripts/probe_vector_rag.py`

> 下面这一节是**初版小语料**上的结果。语料扩到 84 篇之后指标掉了约 10 个点，
> 对比见下一节「探针一之二」——**这一节的漂亮数字有一部分是语料太小造成的假象**。

### ★ 先看标准指标：它们全都很漂亮

| 指标 | k=3 | k=5 | k=10 |
|---|---|---|---|
| **Recall@k** | 0.797 | **0.930** | 1.000 |
| **Precision@k** | 0.667 | 0.520 | 0.280 |
| **Hit Rate@k** | **1.000** | **1.000** | **1.000** |
| **NDCG@k** | 0.938 | **0.945** | 0.979 |
| **MRR** | — | **1.000**（与 k 无关） | — |

单看这张表，这套系统近乎完美：

- **MRR = 1.000** —— 每一道题，排在第 1 位的都是相关文档，一次都没错
- **Hit Rate@k = 1.000** —— 每道题都至少召回了一篇相关文档
- **Recall@5 = 0.930 / NDCG@5 = 0.945** —— 换成百分制就是 93 分和 95 分

**如果只报这些指标，结论会是"检索质量很好，可以上线了"。**

### 但同一份数据，换个判定就崩了

| 类别 | Complete Recall@3 | @5 | @10 |
|---|---|---|---|
| 对照组·单点事实 | **3/3** | **3/3** | **3/3** |
| 多跳推理 | 1/3 | 2/3 | 3/3 |
| 全局聚合 | **0/3** | 2/3 | 3/3 |
| 实体消歧 | 1/1 | 1/1 | 1/1 |
| **总计** | **0.500** | **0.800** | 1.000 |

`Recall@5 = 0.930` 和 `Complete Recall@5 = 0.800` 之间的差，就是这个项目存在的理由。

### 为什么标准指标在这里会骗人

看"全局聚合"这一类的具体数字：

| | 值 | 听起来 |
|---|---|---|
| Recall@5 | **0.933** | 很好 |
| NDCG@5 | **0.956** | 很好 |
| MRR | **1.000** | 完美 |
| Complete Recall@5 | 0.667 | 一般 |
| **实际答案** | **73 人，真值 84** | **错的** |

问「公司总共多少人」，5 篇部门文档召回了 4 篇——**Recall = 0.8，指标上是个不错的分数**。
但漏掉的那一篇是财务部，于是答案少算 11 人。

**Recall@k 是为「找到相关的就算成功」的场景设计的**——搜索引擎、推荐系统都是这样：
你给用户 10 条结果，命中 8 条就是好系统，用户自己会挑。

**但聚合类问题不是这样：漏一篇 = 答案错。** 0.8 的 Recall 在这里不是"80 分"，是"0 分"。

> 这就是为什么必须自己定义 Complete Recall@k，并且**两个都报**。
> 只报标准指标 → 系统看起来 93 分，实际会静默答错。
> 只报 Complete Recall → 又丢掉了和文献、和面试官对话的共同语言。

### 逐题最小可答 k

「最小可答 k」= 要把这题的**全部**必需文档都捞齐，top_k 得开到多大。
这不是标准指标，是 Complete Recall 的逐题版本，用来定位到底是哪几题拖后腿。

| 问题 | 类别 | 最小可答 k |
|---|---|---|
| 后端组有多少人？ | 单点事实 | 1 |
| 二线城市住宿一晚最多报多少钱？ | 单点事实 | 1 |
| 入职满三年有几天年假？ | 单点事实 | 1 |
| 李伟负责什么工作？ | 实体消歧 | 2 |
| 陈刚和刘洋是同一个部门的吗？ | 多跳 | 3 |
| Alpha 项目的产品侧对接人向谁汇报？ | 多跳 | 4 |
| 公司一共有几个部门，分别是什么？ | 全局聚合 | 5 |
| 哪个部门的人最多？ | 全局聚合 | 5 |
| **张敏的上级的上级是谁？** | 多跳 | **6** |
| **公司总共大约多少人？** | 全局聚合 | **6** |

### 读出来的三件事

**1. 对照组 3/3 全绿，说明实现没有 bug。**
这一栏存在的意义就是防止把向量检索讲成稻草人——后面的失败是范式问题，不是代码问题。

**2. 失效有清晰的梯度，而且和问题类型强相关。**
单点事实 k=1 就够；全局聚合要 k≥5，k=3 时 Complete Recall 是 **0/3**，一道都答不了。
而同样这一类的 Recall@3 并不低——**梯度只在严格判定下才看得见**。

**3. 调大 top_k 能"解决"问题，但代价大到没有意义。**
全局聚合类要 k=10 才全绿——语料总共只有 15 篇，**k=10 意味着把三分之二的语料塞进上下文**。
这时候检索基本没起作用，等于退化成"全量塞给模型"。所以答案是：
**这类问题不能靠调参解决，它是范式问题。**

## 探针一之二：扩语料到 84 篇之后

原语料 15 篇 / 1951 字符时，向量检索的指标顶到了天花板（MRR=1.000、Hit@k=1.000），
**没有提升空间就没法证明任何检索侧改进有效**。所以扩到 84 篇 / 18834 字节，
并刻意植入向量检索的盲区（`scripts/gen_corpus.py`，盲区词表 `eval/blindspots.json`）。

### 发现 A：小语料上的漂亮数字确实是假象

同样那 10 道题，只是语料从 15 篇变成 84 篇：

| 指标 | 15 篇 | 84 篇 | 变化 |
|---|---|---|---|
| MRR | 1.000 | 0.950 | −0.050 |
| Recall@3 | 0.797 | 0.690 | **−0.107** |
| Recall@5 | 0.930 | 0.823 | **−0.107** |
| NDCG@5 | 0.945 | 0.839 | **−0.106** |
| Complete Recall@5 | 0.800 | 0.700 | −0.100 |
| **Complete Recall@10** | **1.000** | **0.800** | **−0.200** |

最后一行最能说明问题：**原来 k=10 能全答对，现在答不全了。**
多跳类 Complete Recall@3 从 1/3 掉到 0/3，全局聚合 @10 从 3/3 掉到 2/3。

> **题一道没变，代码一行没改，只是语料大了 5.6 倍，指标就掉了 10 个点。**
> 这条本身就是结论：**在玩具规模的语料上得出的检索指标不能外推。**

### 发现 B：我关于"盲区"的假设，一半是错的

植入了 48 个盲区词，分六类。原假设是"编号、型号、缩写、罕见人名都是向量检索的弱项"。
实测：

| 类型 | Recall@5 | NDCG@5 | **MRR** | 假设对不对 |
|---|---|---|---|---|
| 产品型号（X7-Pro、S3-Max…） | 1.000 | 1.000 | **1.000** | ❌ **错了，完全没问题** |
| 英文缩写（SLA、RTO、QPS…） | 1.000 | 1.000 | **1.000** | ❌ **错了** |
| 罕见人名（郗昭、乜文渊…） | 1.000 | 1.000 | **1.000** | ❌ **错了** |
| 项目编号（PRJ-2026-0142…） | 1.000 | 0.815 | **0.750** | ✅ 对 |
| 工单编号（TICKET-88231…） | 1.000 | 0.782 | **0.708** | ✅ 对 |
| **会议编号（MTG-20260415-03…）** | 0.875 | 0.572 | **0.489** | ✅ **最严重** |

### 发现 C：真正的盲区不是"编号"，是"前缀相同、只有数字不同的编号"

把两组放一起看，规律非常清楚：

| 分得清的 | 分不清的 |
|---|---|
| `X7-Pro` / `S3-Max` / `K2-Air` | `PRJ-2026-0142` / `PRJ-2026-0155` / `PRJ-2026-0163` |
| `SLA` / `RTO` / `QPS` | `TICKET-88231` / `TICKET-88407` / `TICKET-88512` |
| `郗昭` / `乜文渊` / `邝允中` | `MTG-20260415-03` / `MTG-20260422-01` |
| **字符串本身语义可区分** | **前缀完全一样，只差几位数字** |

看具体的失败样本——**召回回来的全是"同类但不是那一个"**：

```
问：MTG-20260617-02 这次会议的决议是什么？
前三名：MTG-20260508-02、MTG-20260701-05、MTG-20260519-04    ← 全是别的会议
正确答案排第 8

问：工单 TICKET-88823 是什么问题？
前三名：TICKET-88512、TICKET-88231、TICKET-88407             ← 全是别的工单
正确答案排第 4

问：PRJ-2026-0163 是哪个项目？
第一名：PRJ-2026-0142                                        ← 错的那个
正确答案排第 2
```

对照组的普通问题，全部**排名第 1**。

**向量检索能准确判断"这是一篇会议纪要"，但完全分不清是哪一篇。**

因为 `MTG-20260415-03` 和 `MTG-20260617-02` 转成向量之后几乎是同一个点——
差异只在几位数字上，而数字在语义空间里几乎不携带信息。

### 发现 D：所以问题在**排序**，不在**召回**

注意项目编号和工单编号的 `Recall@5 = 1.000`——**东西都召回来了**，
只是正确的那篇排在第 2、第 4、第 8 位。

| | 值 | 说明 |
|---|---|---|
| Recall@5 | 1.000 | 找得到 |
| MRR | 0.489~0.750 | **但排不对** |

这个区分很重要，因为它决定了该修什么：

- 如果是**召回**问题 → 要扩大候选集、改 embedding 模型
- 是**排序**问题 → **精确匹配就能解决**：BM25 / 全文检索对 `TICKET-88823`
  这种词是精确命中，会直接把它顶到第一

**这就是混合检索（向量 + 关键词，用 RRF 融合）的确切用武之地**，
而且现在有了可验证的目标：**这三类的 MRR 从 0.489~0.750 提到接近 1.000。**

### 一句话

> 之前想做混合检索，理由是"教程都这么写"。
> 现在的理由是：**三类编号型查询的 MRR 只有 0.49~0.75，而问题在排序不在召回，
> 精确匹配正好补这个短板。** 目标数字也定死了。

## 探针一之三：做混合检索之前，先排除更便宜的方案

在动手做混合检索之前，把两个「也许不用这么麻烦」的可能性测掉。

### 排除一：调切分参数 —— **现在根本测不了**

```
文档长度：中位数 91 字符，最长 164，最短 40
chunk_size = 800
切出来的片段：84 个 / 84 篇      ← 每篇正好一片
只切成 1 片的文档：84 篇
切成 2 片以上的：  0 篇
```

**切分逻辑一次都没被触发过。** 生成的文档全都远短于 `chunk_size`。

所以「换个切分策略试试」在当前语料上是无意义的操作——不管怎么调，
只要 `chunk_size > 164`，结果一模一样。

> 这是**当前语料的已知局限**：要评估切分策略，得先有长文档（几千字的报告、手册）。
> 记在这里，别在这上面浪费实验。

### 排除二：MRL 截断损失了信息？—— **不是**

我们把 embedding 从 4096 维截断到 1024 维。合理怀疑：
细粒度的区分（几位数字之差）正好丢在被截掉的尾部维度里。

直接量化——对同一个查询，比较 8 篇会议纪要的相似度分布：

| | 正确答案排名 | 第一二名差距 | **全体相似度跨度** |
|---|---|---|---|
| **会议编号**（盲区）1024 维 | 第 **8** 名 | +0.0074 | **0.0726** |
| **会议编号**（盲区）4096 维 | 第 **8** 名 | +0.0075 | **0.0503** |
| 普通问题（对照）1024 维 | 第 1 名 | +0.2391 | 0.3957 |
| 普通问题（对照）4096 维 | 第 1 名 | +0.2167 | 0.3679 |

两个结论：

**① 升到 4096 维完全没用。** 正确答案还是排第 8，差距还是 0.0075。
**MRL 截断不是原因**，这条假设可以划掉了（同时也补上了 RESULTS.md 里
"MRL 截断的质量影响没测过"这个缺口——**答案是：对这类查询没影响**）。

**② 问题被量化了。** 8 篇会议纪要的相似度跨度只有 **0.0726**，
而普通问题是 **0.3957**——**差 5 倍以上**。

它们在向量空间里几乎是同一个点。而且正确答案排**最后一名**，
说明编号里的数字对相似度**几乎零贡献**，排序完全由别的内容（会议主题的措辞）决定。

> 这也说明换个 embedding 模型大概率也没用——**数字在稠密向量里不携带区分信息，
> 这是范式特性，不是模型缺陷。**

### 验证：关键词匹配能不能补上这个短板

在写任何代码之前，先用最粗糙的方式模拟一下——把问题里的编号/型号/缩写当关键词，
做精确子串匹配，看能不能唯一命中正确文档：

| 类型 | **关键词唯一命中** | **向量检索 MRR** |
|---|---|---|
| 会议编号 | **8/8** | **0.489** ← 向量最差，关键词满分 |
| 项目编号 | **8/8** | 0.750 |
| 工单编号 | 5/6 | 0.708 |
| 产品型号 | 1/8 | **1.000** ← 向量满分 |
| 英文缩写 | 6/10 | **1.000** |
| 罕见人名 | 8/8 | 1.000 |

**两边的强弱恰好互补：向量最差的三类（编号），正是关键词最强的三类。**

> **这个模拟很粗糙**，只判"是否唯一命中"。产品型号的 1/8 不代表关键词检索差——
> `X7-Pro` 同时出现在产品文档、相关会议纪要、相关工单里，子串匹配返回 3 篇就算"不唯一"。
> 真正的 BM25 会做 TF-IDF 加权，标题命中的那篇会排在前面。
> 所以这张表**只能证明"编号类上关键词强于向量"这一条**，那一条已经足够。

## 结论：混合检索是对的下一步，而且理由是测出来的

| 方案 | 结论 | 依据 |
|---|---|---|
| 调切分参数 | ❌ 当前语料测不了 | 84 篇文档全都短于 `chunk_size`，切分从未触发 |
| 提高 embedding 维度 | ❌ **无效** | 4096 维下正确答案仍排第 8，差距仍是 0.0075 |
| 换 embedding 模型 | ⚠️ 大概率无效 | 数字在稠密向量里不携带区分信息，是范式特性 |
| **混合检索（向量 + 关键词 + RRF）** | ✅ **该做** | 两边强弱互补；编号类关键词唯一命中 8/8，向量 MRR 仅 0.489 |

**可验证的目标：编号三类的 MRR 从 0.489 / 0.708 / 0.750 提到接近 1.000，
同时产品型号 / 英文缩写 / 罕见人名三类的 1.000 不能掉。**

后一半和前一半一样重要——**融合的风险就是把原本对的搞坏**。

### 但过程翻了两次车，翻车比结果更值得记

#### 翻车一：朴素 RRF 把原来 10 道题的 Recall@5 从 0.803 打到 0.610

第一版是标准做法：向量排名 + 全量 BM25 排名 → RRF 融合。
盲区确实修好了（会议编号 0.489 → 0.906），但普通问题崩了。

典型样本：

```
问「哪个部门的人最多？」
  向量：dept-tech / dept-hr / dept-product / dept-finance / dept-market   ← 5 篇全对
  BM25：metric-rpo / policy-team-building / policy-recruit / ...          ← 全错
  融合：垃圾把对的挤掉了
```

**根因：BM25 在没有区分性信号时，仍然会输出一个"看起来很自信"的排名，
而 RRF 只看名次不看分数，把噪声当成了权威。**

#### 我的第一个修法假设被数据否了

直觉是加 IDF 门槛："查询里没有稀有词就不启用 BM25"。测了一下：

| 查询 | 最稀有词 | 出现在几篇 | 融合效果 |
|---|---|---|---|
| MTG-20260617-02 … | `20260617` | 1 | ✅ 修好 |
| 工单 TICKET-88823 … | `88823` | 1 | ✅ 修好 |
| **哪个部门的人最多？** | **`最多`** | **1** | ❌ **被搞坏** |
| **陈刚和刘洋是同一个部门的吗？** | **`同一`** | **1** | ❌ **被搞坏** |
| 入职满三年有几天年假？ | `天年` | 1 | = 保持 |

**「最多」「同一」「天年」在语料里只出现 1 次，和精确编号一样稀有。**
稀有度分不开这两组。

`天年` 是从「三年年假」切出来的**伪词**——中文二元组切分的副产品，根本不是一个词。

#### 真正的分界线是 token 的**类型**，不是稀有度

| | 稀有性的来源 | 向量能不能处理 |
|---|---|---|
| 拉丁/数字 token（`20260617`、`sla`、`x7-pro`） | 真实语义信号 | **不能**——这正是盲区 |
| 中文二元组（`最多`、`同一`、`天年`） | 分词方式的副产品 | **能**——语义匹配是向量强项 |

所以规则改成：**关键词路只负责标识符，中文交给向量。**
查询里没有标识符时，BM25 一分不贡献，退化成纯向量——那本来就是它该做的。

改完：原来 10 道题的 Recall@5 从 0.610 恢复到 0.823（= 纯向量），零损伤。

---

#### 翻车二：项目编号纹丝不动（0.750 → 0.750），而关键词单独跑是 1.000

诊断发现是**结构性平局**，8 题里 4 题栽在这上面：

```
向量：  错的那篇 第1，正确答案 第2
关键词：正确答案 第1，错的那篇 第2
RRF：   两边都是 1/61 + 1/62 = 0.032522   ← 完全相等
```

两篇文档在两个排名里占据的名次集合都是 `{1, 2}`，**分数必然相同**。

**而且调 k 解决不了**——k=10 也一样平（0.174242 vs 0.174242）。
任何对称的 RRF 都破不了这个局。已写成测试钉死（`test_tie_is_independent_of_k`）。

原来的平局规则是"按下标升序"，纯粹为了可复现，**没有任何检索学上的意义**。
改成"按关键词路的名次破平"，项目编号立刻 0.750 → **1.000**。

> 这不是加权：它只影响**原本就完全相等、只能靠任意规则决定**的情况。
> 不引入需要调参的权重，也就不存在"在测试集上调参"的问题。

---

### 已知代价：英文缩写 1.000 → 0.950

破平规则让关键词在平局时说了算。我原本的理由是"关键词已被标识符门槛限制，
首位命中几乎必对"——**这句话只对编号成立，对缩写不成立**：

| | 语料里出现次数 | BM25 可靠性 |
|---|---|---|
| 编号 `PRJ-2026-0163` | **1 次**（就它自己那篇） | 命中即确定 |
| 缩写 `QPS` / `P0` / `P1` | 正当地出现在多篇里 | 按词频排，选"提得最多的"而非"下定义的" |

实测：

```
问「QPS 的口径是怎么规定的？」
  向量：  metric-qps.md 第 1        ← 语义上"口径规定"就该匹配定义文档
  关键词：runbook-capacity.md 第 1（那篇提了两次 QPS），metric-qps.md 第 2
```

代价：10 题里 1 题的正确答案从第 1 名变第 2 名。**仍在 top-5 内，不影响 Recall。**

换来的是编号三类合计 +0.792、全局 MRR 0.855 → 0.950。**接受。**

**没有采纳的更精细方案**：只在"命中词的文档频率极低"时才让关键词破平。
它能同时保住那 0.050，但要引入一个文档频率阈值——而那个阈值只能在评测集上选，
本项目没有独立验证集。**为了 1 道题的第 1 名 vs 第 2 名引入一个调参自由度，不值。**

这个取舍写成了测试（`test_tie_breaker_trades_precision_for_coverage_knowingly`），
以后谁想"修好"它，必须先看到自己在交换什么。

### 关键词路为什么是自己写 BM25

PostgreSQL 的 `to_tsvector` 不认中文——需要 zhparser / pg_jieba 扩展，
要改部署、要改 CI、要在镜像里编译。而 BM25 是这个领域的标准算法，
自己实现一遍反而更清楚它在算什么。

代价说清楚：**内存版**，和向量侧的 numpy 余弦一样把可见片段全量拉进来。
几万条以上要换 PG 全文检索或专门的检索引擎，见 SCALING.md。

## 探针四：Agentic RAG —— 测完发现**不用做**

`uv run --no-sync python scripts/probe_agentic.py --rounds 3`

### 我原本的判断，错了两处

打算做多轮检索时，我的依据是两条：

1. 「多跳题 Complete Recall@3 = 0.00，第二跳文档排 7~14 名」——**这条是对的**
2. 「86 次真实调用里续查一次都没发生过」——**这条是错的**

第二条的数据来自 **43 题路由集**，而那套题几乎没有多跳题。
**拿错了数据集，得出了错误的结论。**

于是先补了 15 道真多跳题（`eval/probes_multihop.json`，每道都验证过
"第二跳文档里不含问题中的实体"），在 **Agent 层**而不是检索层重新测。

### 结果（24 题 × 3 轮 = 72 次运行）

| 分组 | 续查触发率 | 答案正确率 | 平均调用次数 |
|---|---|---|---|
| 多跳·新增（15 题） | **71.1%** | **100.0%** | 2.13 |
| 多跳·原有（3 题） | **88.9%** | 88.9% | 2.78 |
| **对照·单点事实（3 题）** | **0.0%** | **100.0%** | **1.00** |
| 全局聚合（3 题） | 0.0% | **100.0%** | 1.22 |

**能力早就在了，而且是自适应的**：

- 需要多跳 → 触发 71~89%
- 单点事实 → **触发 0%**，每题正好 1 次调用
- 成本也自适应：1.00 次 vs 2.13~2.78 次

> **这正是上一轮给关键词路加"标识符门槛"时追求的性质**——
> 能力要有，但要在对的时候才用。这里它自己就做到了，不需要额外规则。

### 意外发现：跨链路多跳

第一次跑的时候，5 道题被判"文档链覆盖失败"。查下来是**我的指标错了**：

```
[mh-04] Eta 项目的负责人所在的组，属于哪个部门？
  工具调用：vector_search → table_query
  答：Eta 项目由会计组承担，负责人是曹敏[1]。会计组属于财务部[2]。   ← 完全正确
```

Agent 走的是 **文档 → 表格** 的跨链路多跳：第一跳在文档里查到"会计组"，
第二跳直接查花名册。**这比在文档里再查一次更好**——花名册才是组织归属的权威来源。

我原来的"覆盖率"只统计 `vector_search` 检索到的文档，把这个正确行为判成了失败。
已改名为"文档链覆盖率"并注明它会低估系统，**以答案正确率为准**。

15 道多跳题里 6 道走跨链路、9 道走文档续查，**全部答对**。

### ★ 探针三那个失败，闭环了

整个项目最早那条数据——问「公司总共大约多少人」，答 **73 人**（真值 84），
而且答得列了明细、标了来源、看不出错。

现在：

```
第1轮  工具：['table_query']  答：公司目前总人数为 84 人 [1]
第2轮  工具：['table_query']  答：公司总人数为 84 人 [1]
第3轮  工具：['table_query']  答：公司总共 84 人 [1]
```

**三轮全对。** 修好它的不是任何检索优化，是**路由**——把这题送去了表格链路，
`sum()` 不会漏行。这正是这个项目最初的主张。

---

### 唯一的真实缺口：1.4% 的"查到耗尽"

72 次运行的工具调用分布：

| 调用次数 | 运行数 |
|---|---|
| 1 次 | 18 |
| 2 次 | 42 |
| 3 次 | 11 |
| **6 次（上限）** | **1** ← 失败 |

那一次：

```
[hop-1 第2轮] 张敏的上级的上级是谁？
  工具调用：vector_search × 6      ← 耗尽 max_steps
  答：超过最大工具调用轮数仍未得到结论，请把问题问得更具体一些。
```

同一道题三轮的调用次数是 `[3, 6, 3]`——**不稳定**。

**所以真正缺的不是"会不会续查"，是"知不知道什么时候停"。**
对应面试题库里反复出现的那一类：「Agent 死循环怎么解决」「停止判定怎么设计」。

**没有立刻修**，理由是诚实的：**n=1，改完也没法证明改好了。**
要修得先把样本做出来（比如跑 20 轮，或者构造更多容易跑飞的题），
否则就是"改了个看起来合理的东西，但不知道有没有用"。已记进待办。

---

### 这一节最该记住的

> **测完的结论是"不用做"。**
>
> 如果直接按原计划改 system prompt 加续查规则，我会得到一个"看起来有效"的改动
> ——因为续查率本来就有 71%，加了规则大概还是 71%，然后我会以为是自己的功劳。
>
> **先测基线，才知道它已经在工作了。** 而且顺带发现了跨链路多跳、
> 修正了一个错误的指标定义、闭环了项目最早的那条失败数据、
> 定位到了真正的缺口（不会停，不是不会查）。

## 探针二：多跳失败是"召回率不够"还是"召回时机不对"

`uv run --no-sync python scripts/probe_multihop.py`

这个区分决定了往哪个方向修，所以值得单独做一次对照实验。

- 题目：**张敏的上级的上级是谁？**
- 必须召回：`dept-tech.md`（技术部 → 李伟）
- 两种方式**用同样的 top_k = 3**

| | 检索方式 | 召回结果 | 结论 |
|---|---|---|---|
| 方式一 | 拿原问题直接检索一次 | team-backend, dept-product, dept-finance | ✗ **漏掉 dept-tech.md** |
| 方式二 | 先查「张敏」，读到桥接事实后再查「后端组属于哪个部门」 | 第1步：team-backend…<br>第2步：team-backend, **dept-tech**, dept-product | ✓ **命中** |

### 结论

**同样的 k，单次检索失败，两步检索成功。**

信息一直都在库里。缺的不是召回能力，是「**读完第一跳再决定下一步查什么**」这个环节——
单次检索在架构上就没有这个环节。

`dept-tech.md` 里根本没有"张敏"两个字，所以拿原问题去检索，它在语义上就排不进前 3
（实测排第 6）。而一旦知道了"张敏 → 后端组"这个桥接事实，用「后端组属于哪个部门」
去查，它立刻排到第 2。

这直接指向两条修法，且是两个不同方向：

| 修法 | 改什么 | 对应实现 |
|---|---|---|
| 改变**知识组织** | 把关系预先抽成图，多跳变成图遍历 | GraphRAG |
| 改变**检索过程** | 让 Agent 迭代检索，自己决定下一跳 | Agentic RAG |

**注意：调 k、换 embedding 模型、加 rerank 都在第三条路上，它们解决不了这个问题**——
因为问题不在排序质量，在于第一次检索时你还不知道该查什么。

## 探针三：召回不全时，模型会说"我不确定"吗

`uv run --no-sync python scripts/probe_silent_error.py`

这是 RAG 在企业场景最危险的失效模式：**不是答不出来，是答错了但看起来对。**

- 问题：**公司总共大约多少人？**
- 真值：技术部 32 + 产品部 14 + 市场部 18 + 人力资源部 9 + 财务部 11 = **84 人**
- top_k=5 召回：`dept-hr, dept-tech, dept-product, dept-market, intern-liwei`
- **漏掉：`dept-finance.md`**（财务部 11 人）

模型基于这 5 条片段给出的回答：

> 根据检索到的信息，人力资源部9人、技术部32人、产品部14人、市场部18人，合计约73人。

| 判定项 | 结果 |
|---|---|
| 漏召回部门数 | 1 |
| 模型是否声明信息不完整 | **否——静默给出了答案** |
| 答案误差 | 73 vs 84，**少算 11 人（13%）** |

### 为什么这是最该被记住的一条

这个回答**列了明细、标了来源、算术完全正确、语气自然**。
用户拿到它，没有任何线索能察觉少了一个部门。

**检索的缺陷被生成层完美地掩盖了。** 模型不会为"我没看到的东西"负责——
它只看到 4 个部门，就诚实地把这 4 个加起来了。

这条数据是"RAG 需要评测体系而不是靠体感"最直接的论据：
如果只是人工点几下看看效果，这个回答百分之百会被判为"答得挺好"。

## 还没测的（诚实的缺口）

**检索侧（本文件）**

- **切分策略对比**：当前语料**测不了**——84 篇文档中位数仅 91 字符，全都短于 chunk_size=800，
  切分逻辑从未触发。要评估切分必须先有长文档
- ~~**MRL 截断的质量影响**~~ → 已测：对编号型查询**无影响**（4096 维下正确答案仍排第 8）。
  其它查询类型的影响仍未系统测量
- **混合检索**：只有向量检索，没有 BM25 / 关键词召回，也没有 rerank。
  但现在有明确目标了：编号型查询的 MRR 从 0.489~0.750 提到接近 1.000（见探针一之二）
- **延迟与成本**：没有 benchmark

前两条在代码注释里曾以结论形式出现过，但这个项目里没有支撑它们的实验——
在补上数据之前，它们只能算待验证的假设。

**Agent 层**

- **停止判定**：72 次运行里有 1 次（1.4%）查到耗尽 max_steps 且没给出答案。
  同一道题三轮调用次数 `[3, 6, 3]`，不稳定。n=1，修之前要先把样本做出来。

**生成侧（完全空白）**

RAGAS 那一类指标——**Faithfulness**（答案里的话能否被检索到的原文支持，即防幻觉）、
**Answer Relevancy**、**Context Precision / Recall**——一个都没做。

这是刻意的取舍，理由和代价都要说清楚：

| 为什么没做 | 代价 |
|---|---|
| 这几个指标都要用另一个 LLM 当裁判，**不确定性会叠加**——被测系统本身就有 ±5pp 波动，再叠一个随机裁判就分不清是系统变了还是裁判变了 | **幻觉完全没被量化** |
| 裁判给的分数**没法调试**：faithfulness = 0.72 不告诉你该改哪里，而"doc-08 该走文档却走了表格"直接告诉你改什么 | 答案是否忠于原文，目前只能人工看 |
| 要花钱、要联网、要几分钟，**进不了 CI** | |
| 项目处在"建立基线"阶段，第一个数字必须绝对可复现 | |

补的话，第一步可以做一个**不用 LLM 的廉价 groundedness 检查**：
把答案里出现的数字抽出来，检查是否都能在检索到的原文里找到。
抓不了全部幻觉，但零成本、可复现、能进 CI。
