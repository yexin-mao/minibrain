## 表面上的结论（**但见下面的缺陷**）

判据是事先定死的：`rerank 20→5` 要在 `CompRecall@5` 上追平或超过
`baseline@10`，**同时** context 字符显著更少。

两条都过了：0.793 > 0.741，且 476 字 vs 1,060 字（**少 55%**）。
NDCG@5、Recall@5、MRR 也都赢。

小池子 `rerank 10→5` 在 `CompRecall@3` / NDCG@5 / MRR 上反而最好，
但 `CompRecall@5` 输给大池子。读出来的取舍是：
**小池子排得更准，大池子捞得更全。**

## ★★ 为什么这些数字不能用

### 缺陷一：分不出「真的重排了」和「压根没排」

实测同一个模型、同一个提示词、`temperature=0`，输出**极不稳定**：

```
一次调用：输出 583~687 token（完整排序）    耗时 12~16 秒
另一次：  输出 4 token，内容是 `[1]`
```

而 `_parse_order` 会把模型没提到的候选按原顺序补齐。所以模型只回 `[1]` 时，
结果 ≈ 原顺序 —— **重排等于没做**，可 `fell_back` 是 `False`，代码报告「成功」。

跑这次消融时还没有 `partial` 标记，**所以无法知道 174 次调用里有多少是空转**。

方向仍然可信（空转只会稀释收益，不会造出收益），
但**幅度不可信**——真实收益可能比 0.741→0.793 更大，具体多少不知道。

这个实现后来被整体删除，因此不再维护解析器或对应单元测试。

### 缺陷二：位置偏见那 3 题可能是假象

「10 题里 3 题换个顺序就换了第一名」这个数字，前提是每次都真的排了序。
如果其中几次模型只回了 `[1]`，那「第一名」就是**展示顺序的第 1 个**——
打乱和不打乱必然不同。所以那 3 题里可能混着缺陷一的假象。

### 缺陷三：地基是未验证的

整个消融跑在 `CHUNK_SIZE=800 / CHUNK_OVERLAP=120` 上，而这两个数字**从没验证过**。
切分消融（`scripts/ablate_chunking.py`）如果得出别的最优值，这张表要重跑。

**顺序错了**：应该先定地基再调上层。这条我自己写在 `ablate_chunking.py` 的
docstring 里，然后违反了。

## 重跑之前要满足的条件

1. 切分消融跑完，`CHUNK_SIZE` / `CHUNK_OVERLAP` 定下来
2. 消融脚本统计并报告 `partial` 比例
3. 连跑两次，结论一致

三条都满足才把结果写进 `eval/RESULTS.md`。

## 一个已经站得住的判断

不管幅度如何，**LLM listwise 重排 12~16 秒的延迟在生产里不可用**。
真要上线一定是换 cross-encoder（本地）或商用 rerank API。

所以**不要再去调这个实现的提示词**——那是在优化一条注定被替换的路。
这次实验的价值是证明了“候选选择可能改善固定 context 下的排序”，但没有证明
“多一次生成模型调用值得上线”；后一个问题改由 MMR 和可选 cross-encoder 回答。
